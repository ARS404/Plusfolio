# Приглашения по почте

В серверной версии работает отправка индивидуальных приглашений через SMTP выбранного провайдера. Собственный почтовый сервер на VPS не нужен. В локальной демке интернет-отправка выключена: письма доступны в локальном ящике интерфейса. Установка и параметры — в [серверной инструкции](server-deploy.md).

## Что нужно от владельца

Один раз указать домен сайта, SMTP-хост/порт, логин, пароль и адрес отправителя. Для порта 587 используется STARTTLS, для 465 — SSL. Домен сайта должен указывать на сервер; отправляющий домен должен быть подтверждён у провайдера. SPF, DKIM и DMARC настраиваются в DNS по его инструкции. Это подтверждает отправителя, но не гарантирует попадание во входящие.

Установщик спрашивает эти параметры, скрывает ввод паролей, сохраняет их в закрытом каталоге `.deploy`, проверяет соединение и SMTP-авторизацию. При этой проверке письмо не отправляется. Для проверки реальной доставки создайте приглашение на свой адрес через интерфейс и примите его в отдельной сессии браузера.

## Порядок работы

1. В интерфейсе «Приглашения» отправитель указывает email, роль и разрешённую область доступа.
2. API проверяет права и остаток общего почтового лимита, затем в одной транзакции создаёт инвайт и задание почтовой очереди. В ответе сразу доступно состояние отправки. При нехватке лимита возвращается HTTP 429 с уведомлением; приглашение и письмо не создаются. Набор приглашений в несколько кружков либо создаётся полностью, либо отменяется целиком.
3. Отдельный worker забирает задания с блокировкой строки и ограниченным временем владения. Несколько процессов не отправляют одно задание одновременно. После падения процесса задание можно забрать повторно.
4. Перед SMTP-отправкой повторно проверяются срок, отзыв инвайта и текущие права отправителя.
5. Письмо содержит название Plusfolio, кружок при наличии, срок действия и ссылку на настроенный HTTPS-адрес приложения. Школьник заполняет ФИО и год выпуска при регистрации. Существующий пользователь входит под приглашённым email и принимает новую роль.
6. Только принятие приглашения выдаёт доступ. Открытие ссылки по GET, например почтовым сканером, не принимает приглашение.

В интерфейсе отдельно показываются состояние приглашения и состояние отправки письма. Пока письмо ожидает обработки, список обновляется автоматически.

| Отправка | Значение |
| --- | --- |
| В очереди | Worker ещё не передал письмо SMTP-серверу |
| Повтор | Временная ошибка; повтор запланирован |
| Отправлено | SMTP-сервер принял письмо; получение/прочтение не подтверждено |
| Ошибка | Постоянный SMTP-отказ либо исчерпаны попытки |
| Отменено | Приглашение недействительно либо исчерпан суточный лимит отправки |

Всего разрешено восемь попыток. Задержка увеличивается от 30 секунд до одного часа; постоянные SMTP-отказы останавливают повторы. При окончательной ошибке проверьте адрес и настройки SMTP, затем создайте новое приглашение. Ошибки в API содержат только безопасный код без текста ответа провайдера.

SMTP допускает повтор после сбоя между приёмом письма провайдером и сохранением статуса в БД. Для одного задания сохраняется одинаковый Message-ID и та же одноразовая ссылка. Повторное принятие не создаёт повторное участие или аккаунт. Статус «Отправлено» не означает гарантированную доставку в почтовый ящик.

## Общий лимит писем

По умолчанию весь сервис может отправить **100 писем в календарные сутки по Москве**. Все SMTP-отправки через почтовый backend Django используют один счётчик в БД, независимо от типа письма и количества процессов. Письмо нескольким адресатам учитывается по числу получателей, включая CC/BCC. Неудачные и неопределённые попытки SMTP тоже расходуют лимит: после сетевого сбоя сервер мог уже принять письмо.

Принятые в очередь приглашения занимают оставшиеся места. При исчерпании лимита интерфейс сообщает: «Сегодня письма отправлять уже нельзя: общий суточный лимит исчерпан». Письма сверх лимита не сохраняются на завтра. Если лимит снизили после создания очереди или его исчерпали повторные SMTP-попытки, обработчик отменяет лишние задания с кодом `daily_limit`; они автоматически не возобновляются.

Посмотреть состояние и изменить лимит на работающем сервере:

```bash
python3 scripts/server.py mail-limit
python3 scripts/server.py mail-limit --set 100
```

`--set 0` останавливает отправку. Изменение действует при следующей проверке без пересборки и перезапуска, не сбрасывает уже использованный счётчик. Значение хранится в БД и попадает в её бэкап. В локальном запуске эквивалентная команда: `.venv/bin/python backend/manage.py mail_limit --set 100`. Демо не отправляет SMTP-письма и не расходует счётчик отправки.

## Секреты и резервные копии

В инвайте хранится хеш токена; содержимое задания зашифровано ключом приложения. SMTP-пароль находится в отдельном файле Compose secret. Адреса получателей, текст письма, токены и ответы провайдера worker не пишет в служебные логи. Полный зашифрованный серверный бэкап включает конфигурацию и секреты; его приватный ключ хранится отдельно.

После восстановления БД старые сессии, API-токены и незавершённые приглашения отзываются, неотправленные письма отменяются. Старая очередь не начинает рассылаться заново. Для выдачи доступа создаются новые приглашения.

## Проверка и дальнейшее развитие

`python3 deploy/check_server.py` проверяет настоящую SMTP-передачу в одноразовый приёмник, регистрацию по полученной ссылке и вступление в кружок. Тесты worker проверяют повтор, постоянный отказ, отмену и блокировку задания. Настоящие внешние адресаты в автоматических тестах не используются.

Webhook-события о доставке/жалобах, список подавления адресов, адаптер API провайдера, массовые рассылки и восстановление забытого пароля не входят в текущий механизм приглашений. Их можно добавить отдельно. Выбранный SMTP-провайдер должен соответствовать требованиям российского размещения проекта.
