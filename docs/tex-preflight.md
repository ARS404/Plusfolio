# Обязательная проверка TeX перед загрузкой

Робот получает `GET /api/v1/tex/toolchain` и `GET /api/v1/tex/toolchain/archive` с тем же Bearer-токеном. Методы доступны преподавателю и администратору, включая токен только для чтения. Архив не содержит БД, ключей или пользовательских документов: только точный сборщик, шаблон, installer, закреплённые зависимости и подготовленный кэш TeX.

Сохраните `contract_id` из JSON. Распакуйте ZIP в отдельный каталог; сверяйте SHA-256 файлов с `toolchain-manifest.json`. Локальная команда также проверяет полный набор файлов и совпадение `--expected-contract` с актуальным сервисом. Репозиторий иной ревизии, произвольный LaTeX и встроенный компилятор редактора не заменяют этот пакет.

## Подготовка один раз для данного пакета

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-tex.lock
.venv/bin/python scripts/preview_tex.py --prepare --expected-contract <CONTRACT_ID_ИЗ_API>
```

Installer загружает официальный Tectonic **0.17.0** с проверкой закреплённого SHA-256 архива для macOS arm64 / Linux x86_64 / Linux aarch64. В архиве уже есть подготовленные offline-ресурсы, включая шрифты; для пользовательского TeX сеть запрещена. На Linux необходим bubblewrap (`bwrap`), на macOS используется `sandbox-exec`. Если среда не поддерживается, компилятор недоступен, хеш не совпал или sandbox не работает, MUST остановить публикацию и задать дополнительный вопрос о продолжении. Не отключать изоляцию и не заменять компилятор.

`--prepare` устанавливает компилятор и проверяет оба шаблона в **временной копии** кэша с `--only-cached`: ресурсы скачанного пакета не дополняются и manifest не меняется. Для нового компилятора интернет может потребоваться только при установке закреплённого бинарного файла.

## Неполный кэш или несовпадение manifest

Ошибка `Toolchain files differ from the downloaded manifest` может возникнуть у старого пакета, если подготовка дозагрузила отсутствующие зависимости `tcolorbox`. Исправлять хеши, удалять manifest или продолжать с изменённым пакетом нельзя. Администратор выполняет `.venv/bin/python scripts/setup_tex.py` на сервере, который выдаёт архив (при контейнерной установке — пересобирает application и compiler из обновлённых исходников), после чего робот заново получает **и JSON контракта, и ZIP** и распаковывает их в новый каталог. Старый `--expected-contract` для нового пакета не подходит.

После успешной автономной компиляции обоих доверенных шаблонов installer сохраняет `plusfolio-prepared.json` с хешами installer, шаблонов и всех ресурсов. Экспорт сверяет эту запись и отказывает при неполном или устаревшем кэше. ZIP и `toolchain-manifest.json` создаются из одного проверенного набора байтов; при изменении файлов во время упаковки незавершённый архив удаляется. Переподготовка ресурсов меняет `contract_id`, поэтому старый ZIP из кэша не выдаётся вместо нового.

В серверном образе доверенные ресурсы находятся в `/app/tex-runtime`, отдельно от постоянного тома `/app/.local`. Обновление образа обновляет ресурсы экспорта; старый кэш в томе не перекрывает новый. Резервная копия берёт ресурсы из текущего образа и сохраняет прежние пути восстановления `source/.local/...`.

Скачивание архива не запускает прогрев, компилятор или копирование кэша. Упаковка идёт в файл порциями до 1 МиБ, выдача — потоком. До хеширования проверяются пределы ресурсов: 256 МиБ и 4096 файлов/каталогов; запись подготовки ограничена 2 МиБ. При превышении лимита ZIP удаляется, готовые архивы ограничены 128 МиБ и двумя файлами. Временная копия ресурсов создаётся только локальной командой `--prepare` и удаляется после проверки, в том числе при ошибке.

## Черновик одной задачи

```json
{
  "kind": "problem",
  "problems": [{
    "title": "",
    "description": "",
    "statement": "<СОГЛАСОВАННОЕ УСЛОВИЕ>",
    "solution": "<СОГЛАСОВАННОЕ РЕШЕНИЕ>",
    "statement_tex": "",
    "solution_tex": ""
  }]
}
```

Для kind=problem заголовок и описание берутся из единственного объекта problems; worksheet используется только при kind=worksheet. Обычные тексты и TeX обрезаются по краям так же, как при сохранении в сервисе. Для существующей задачи передайте её действительный `id`, `title`, обычные тексты, TeX и `attribution` из GET материала. Для новой задачи `id` отсутствует: временные имена `draft-001` нужны только файлам предпросмотра, их нельзя отправлять как UUID в API. Если название новой задачи пусто, служебный заголовок предпросмотра временный; после создания сервис покажет выданный номер. Визуальная проверка содержимого обязательна до POST.

## Сборка

```bash
.venv/bin/python scripts/preview_tex.py --input draft.json --output review-task-001-v1 --expected-contract <CONTRACT_ID_ИЗ_API>
```

Каждая новая редакция получает новый выходной каталог. Команда не загружает настройки приложения, аккаунты или БД и не создаёт задач/листков. Она напрямую вызывает **те же `project_for`, `fragment`, `flatten` и `render_pdf` из `backend/core/documents.py`**, что и сервис. Временный PDF-кэш пустой, поэтому выполняется реальная компиляция обоих вариантов:

- `statement.pdf` — условие без решения;
- `with-solutions.pdf` — условие и решение;
- соответствующие `.tex` и каталоги многофайловых проектов;
- `report.json` — ID пакета, SHA-256 входного JSON, проектов и PDF, версия компилятора и предупреждения сборки.

Статус отчёта `requires_visual_review_and_user_confirmation` НЕ означает согласование. Он требует просмотра и дополнительного вопроса пользователю.

## Что именно повторяется

Основной файл `main.tex` включает `variables.tex` и `template.tex`. Новый шаблон — **math-a4-v2** (прежние листки сохраняют **math-a4-v1**), `article`, 11pt, A4, поля 22 мм, DejaVu Serif/Sans, русский язык через polyglossia, amsmath/amssymb/amsthm/enumitem/TikZ. Файлы условий: `tasks/001-<id>.tex`; решений: `solutions/001-<id>.tex`; текстовые блоки: `blocks/001.tex`; нормализованные рисунки: `assets/<UUID>.png`. Порядок задают `problems.tex` и `solutions.tex`. В v2 подключены graphicx и tcolorbox с переносимыми между страницами окружениями definition/theorem/lemma/example/remark.

В библиотеке переменные кружка, даты и номера равны «НАЗВАНИЕ КРУЖКА», «ДАТА ВЫДАЧИ», «НОМЕР ЛИСТОЧКА». Их нельзя молча заменять текущей датой или предполагаемым кружком. В отдельном PDF задачи сборщик убирает поля выдачи так же, как сервис. На листе решений используется разрыв страницы и исходная нумерация задач.

Непустой `statement_tex` / `solution_tex` имеет приоритет. Если он пуст, обычный текст экранируется, а однострочные `$...$` сохраняются по правилам `fragment()`. Не нужно самостоятельно повторно экранировать текст или собирать другое окружение. TeX-фрагменты не содержат documentclass, usepackage, begin/end document. Подключённые библиотеки TikZ: calc, angles, quotes, intersections, positioning, arrows.meta, decorations.markings, shapes.geometric, patterns, babel. Дополнительные пакеты не подключаются самовольно.

Команда компилятора: `tectonic -X compile --untrusted --only-cached --keep-logs main.tex`. `tex_worker.py` и `render_pdf` обеспечивают те же ограничения: 20 секунд wall time, 12 секунд CPU, PDF/файл до 16 МиБ, суммарно до 64 МиБ и 2048 временных файлов/каталогов, 256 открытых файлов, на Linux адресное пространство до 1 ГиБ. Сеть запрещена; доступны только рабочий каталог, доверенные ресурсы и системные библиотеки/шрифты. Если пользовательский фрагмент требует отсутствующего ресурса, MUST остановиться и обсудить исправление или обновление доверенного пакета.

## Визуальное согласование

Робот MUST открыть оба PDF, отрисовать и просмотреть **каждую страницу**, а не ограничиваться кодом возврата, размером файла или извлечённым текстом. Проверить русский текст, все формулы и индексы, знаки неравенств, переносы, нумерацию, поля, разрывы страниц, TikZ и подписи. Отдельно проверить `warnings` в отчёте: пропавшие символы и переполнения не игнорировать. Проблемные предупреждения исправить; допустимое предупреждение объяснить пользователю.

Показать пользователю оба PDF (или предпросмотр всех страниц) и задать дополнительный вопрос **только по текущей задаче**. После исправления пересобрать и спросить снова. Согласование фиксируется для конкретных `toolchain_id`, `input_sha256` и `pdf_sha256`. Любая правка входа или изменение пакета требует новой сборки и нового согласования вёрстки. Успешная компиляция не доказывает правильность решения.

## Финальный листок

После последовательного согласования всех задач и выбора названия/описания/тем/тегов подготовить `kind=worksheet`, `worksheet={title,description,template_version:"math-a4-v2",numbering_start:0}` и `problems` как массив полных данных уже выбранных задач в согласованном порядке. Выполнить ту же команду в новом каталоге, проверить и согласовать оба PDF целого листка до POST создания листка.

Для смешанного листка дополнительно передайте верхнеуровневый `blocks` в согласованном порядке: `{kind:"problem",problem_id:"UUID"}` либо `{kind:"text",style:"definition",title:"…",text:"…",tex:"",images:[]}`. Массив `problems` содержит полные данные всех задач, на которые ссылаются блоки; для теории без задач он пуст. PNG для `statement_images`, `solution_images` и `blocks[].images` передаются в `assets={"UUID":{"base64":"…"}}`; это те же нормализованные пиксели, которые загрузил сервис. В API сам файл загружается через `POST /api/v1/images`. [Пример и лимиты](worksheet-builder.md).

Этот JSON предназначен только локальному предпросмотру. В POST /api/v1/materials/worksheet можно передать `blocks` из предпросмотра. Совместимый старый массив `problems` содержит **UUID**, а не объекты черновика; `kind` и поля отчёта в API не передаются. В POST задачи передаются ровно согласованные обычные тексты и TeX, использованные при предпросмотре. После получения ID сравнить серверный PDF с согласованным макетом. Байтовое равенство разных PDF не требуется: служебные ID и PDF-метаданные могут отличаться.

## Изоляция серверной версии

В серверном Compose сборщик работает в отдельном контейнере без сети, с read-only корнем, ограничениями памяти/процессов и одним заданием одновременно. Он не получает БД, ключ приложения или SMTP-секреты. Веб-процесс передаёт только разрешённый проект по внутреннему Unix-сокету. Исходники после задания удаляются. scripts/tex_service.py входит в пакет; версия Tectonic, шаблон, offline-ресурсы, аргументы и tex_worker совпадают с локальным процессом. Локальный предпросмотр продолжает использовать sandbox-exec/bubblewrap; не запускайте серверный worker вне поставляемого изолированного контейнера.


## Кеш и временные файлы

Черновые сборки (в редакторе и `preview_tex.py`) не сохраняют PDF в кеш. Для сохранённых материалов кеш ограничен 128 МиБ, 256 PDF и семью днями без обращения; ZIP сборщика — 128 МиБ, два архива и 14 дней. Очистка выполняется автоматически при обращении. После каждой сборки рабочий каталог удаляется; после аварийного завершения следующая сборка удаляет свои оставленные каталоги старше минуты без активной блокировки. `manage.py tex_cache` очищает локальные compiler jobs и автономные previews, но не /tmp отдельного compiler-контейнера и не каталоги подготовки. Remote jobs очищаются следующей remote-компиляцией или исчезают с tmpfs при замене контейнера; setup/receipt jobs — следующей соответствующей подготовкой. Доверенные ресурсы при пользовательской сборке доступны только для чтения. Команда `manage.py tex_cache` показывает фактический размер ресурсов и очищает только созданные сервисом артефакты.

Один PDF ограничен 16 МиБ: oversized cache-файл отбрасывается до полного чтения, чтение результата компилятора также ограничено. render_pdf и транспорт переиспользуют один JSON-буфер; транспорт передаёт заголовок и payload без объединения их в ещё один полный буфер. Это ограничивает дополнительные выделения, но не отменяет память самого проекта/компилятора.

Доверенная подготовка заменяет кэш точным проверенным снимком вместо слияния со старыми bundle. Число записей и байты проверяются до копирования; вложенные ссылки не копируются. Снимки, offline-проверка и прогрев используют leased рабочие каталоги; ошибка копирования/публикации снимка возвращает прежний кэш. Замена состоит из двух переименований, поэтому при принудительном завершении между ними подготовку нужно повторить. Установка/обновление ресурсов должна выполняться одним процессом (в Docker — с блокировкой cache mount), не одновременно с ручным изменением ресурсов.

Leased-каталоги после аварии очищаются соответствующим следующим запуском после 60 секунд; активные lease сохраняются. Произвольные прежние unleased setup/verify каталоги глобально не удаляются. Receipt записывается через отдельную leased задачу; временные receipt-файлы не входят в контракт. Старые обычные файлы прежнего receipt-temp namespace очищаются после суток. Ресурсы в `/app/tex-runtime` не находятся в runtime-томе приложения. Изменение preparation inputs требует нового receipt и нового контракта; прежний manifest не переписывается.



В локальном черновике `worksheet.numbering_start` задаёт 0 или 1 (по умолчанию 1). В API это верхнеуровневое поле `numbering_start`, в том числе у `/worksheets/preview`. У блока задачи `include_in_journal=false` исключает её только из плюсника и прогресса: в предпросмотре и PDF печатаются все задачи и решения с исходными номерами.
