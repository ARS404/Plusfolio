# Аналитика и векторный поиск

Сложные расчёты выполняются на backend. С первого этапа нужны устойчивые факты выдачи, история решений и версионирование определений метрик; графики и дополнительные модели можно развивать позже без изменения учебных статусов да/нет.

## Определение закрытия задачи

Для задачи P и выбранного среза C определим U как **множество уникальных школьников, которым назначали листок с P в срезе C**. Аннулированные выдачи и назначения исключаются. Текущее закрытие:

**closure(P, C) = 100 × |{s ∈ U: solved(s, P) = да}| / |U|.**

Сначала ограничиваем доступные кружки, даты назначений и другие фильтры, затем удаляем дубли школьников. Школьник, которому выдавали P в трёх листках и двух кружках, в общей метрике задачи учитывается один раз. В отчёте каждого кружка он может входить в когорту этого кружка, но сумма строк не становится общим знаменателем.

Пример: в A задачу выдали школьникам 1 и 2, в B — школьникам 2 и 3. Решили 1 и 2. Закрытие A — 2/2 = 100%, B — 1/2 = 50%, общий срез — 2/3 ≈ 66,7%. Среднее 75% не является общим закрытием.

При U = ∅ отображается «нет данных». Выбывшие остаются получателями исторической выдачи. Фильтр текущих участников разрешён как другой явно подписанный срез. Ожидающее приглашение без участия и назначения не создаёт получателя; зарегистрированный школьник, добавленный учителем напрямую, учитывается на общих основаниях после назначения листка.

## Базовые метрики и развитие

| Метрика | Числитель и знаменатель / смысл |
| --- | --- |
| Закрытие задачи | Уникальные решившие получатели / уникальные получатели |
| Закрытие листка | Уникальные решённые пары школьник × задача среди назначений листка / все такие пары |
| Полностью закрыли листок | Получатели, решившие все задачи листка / все получатели листка |
| Прогресс школьника | Уникальные решённые задачи его назначенного среза / все уникальные задачи среза |
| Доля разбора | Разобранные уникальные задачи кружка / выданные уникальные задачи кружка |
| Закрытие по тегу | Решённые уникальные пары школьник × задача с тегом / назначенные пары с тегом |
| Закрытие по теме задачи | Решённые уникальные пары школьник × задача в теме или её подтемах / назначенные пары этих задач |
| Подтверждения по времени | События изменения нет → да с отдельным учётом исправлений и повторных включений |
| Динамика кружка | История закрытия, разбора, выдач и состава по выбранному определению |

В дальнейшем: распределение закрытия по задачам и темам, время до подтверждения, когорты набора, повторное участие, сравнения кружков и периодов преподавания. Учитель видит свой разрешённый срез, аналитик — кружки по тегам, администратор — весь. Персональная аналитика школьника ограничена его результатами.

При нескольких тегах одна задача может входить в несколько групп: суммы групп могут пересекаться. Теги задачи, листка и кружка — разные измерения, один фильтр «теги» не должен неявно смешивать их.

## Срезы по дереву тем

Темы задач и листков выбираются из одного дерева, но в отчёте являются разными фильтрами. «Тема задачи» ограничивает сами задачи; «тема листка» ограничивает персональные назначения листков. Они могут применяться одновременно. Темы листка не наследуются его задачами.

По умолчанию тема включает потомков; режим прямой привязки задаётся явно. Сначала выбирается множество подходящих ID задач или листков, затем считаются уникальные факты. Задача с двумя темами одной ветки не увеличивает ни числитель, ни знаменатель родительского показателя. Проценты подтем не усредняются для получения процента родителя.

Например, школьнику назначены две задачи: P с темами «Треугольники» и «Окружности», Q — только «Треугольники». Решена P. В родительской «Планиметрии» результат 1/2 = 50%, хотя строки подтем показывают 1/2 и 1/1. Это пересекающиеся срезы; складывать их нельзя.

Отчёт фиксирует `topic_catalog_version_id`, поскольку перенос ветки меняет её состав. По умолчанию используется текущая версия дерева; для воспроизводимого исторического среза выбирается сохранённая. События и снимки каталога содержат ID, родителей, подписи и архивность. Перестройка дерева инвалидирует зависимые кэши, а историческая версия отчёта сохраняется.

Тема «Прочее» принадлежит конкретному родителю и учитывается по своему ID, а не по общей подписи. Её метрики считаются по явно связанным материалам, без вычитания других подтем из родителя. При добавлении более точной темы старые назначения в «Прочее» автоматически не меняются.

## Текущий результат и результат за период

У каждого отчёта явно указаны два параметра: **когорта получателей** и **момент оценки результата**. Например, «кому выдали в сентябре, решено на сегодня» отличается от «кому выдали в сентябре, решено на 30 сентября». По умолчанию период когорты применяется к персональной дате назначения, а не к дате первоначальной выдачи листка всему кружку.

Для текущего состояния используется `StudentProblemState`. Для состояния на дату — история событий с последним известным да/нет на момент среза. Снятие и повторная установка отметки не создают нового школьника и не должны дважды увеличивать число решивших.

У событий различаются время записи сервером и эффективная дата учебного действия. Сервис знает время подтверждения, а не точное время решения. У выдачи пользователь задаёт календарную дату; если подтверждение попало в тот же день, нельзя утверждать строгий порядок событий внутри дня. Метрика «подтверждено в дату выдачи или после» подписывается именно так. Внесённые задним числом данные сохраняют и дату действия, и время их записи.

Глобальная решённость означает, что в закрытие попадают решения до выдачи и подтверждения из других кружков. Для дополнительных срезов отдельно выделяются уже решённые к дате выдачи и впервые подтверждённые затем. Ни одна из этих метрик сама по себе не измеряет причинный эффект преподавателя.

При нескольких преподавателях результат относится к кружку и периоду их работы. Автор отметки — это человек, внёсший запись, а не доказанный автор учебного результата. Автоматический рейтинг преподавателей из этих данных не строится.

## Факты, необходимые с первого дня

- Персональные назначения листков и неизменяемый состав листка: кому, что, где и когда выдали.
- Периоды участия школьника и работы преподавателя, без удаления старых связей.
- События решений, разбора, аннулирования ошибочных выдач/назначений и изменений состава.
- Стабильные ID трёх типов тегов и история их административных изменений.
- Общие topic_id, фиксированные привязки задач/листков и версии структуры дерева тем.
- Версия определения метрики и параметры конкретного расчёта.

Факт «задача назначена» получается соединением назначения листка с его пунктами; отдельное дублирование каждой пары в основной схеме необязательно. В аналитической витрине можно материализовать более удобный уровень школьник × кружок × выдача × задача.

Текущая таблица, событие и аудит сохраняются атомарно. Производные расчёты обрабатывают события идемпотентно. События не удаляются без согласованной политики: для удаления персональных данных предусматриваются обезличивание и перестройка производных слоёв.

## Выполнение сложных расчётов

1. **Начало:** параметризованный SQL в PostgreSQL для группировок, дедупликации и оконных расчётов; Django управляет доступом и транзакциями. Backend не ограничивается возможностями ORM, но произвольный SQL от пользователя не принимает.
2. **Повторяемые сводки:** отдельная аналитическая схема, агрегатные таблицы или materialized views, обновляемые worker. Материализованное представление сохраняет результат запроса и обновляется явно. [PostgreSQL о materialized views](https://www.postgresql.org/docs/current/rules-materializedviews.html).
3. **Тяжёлые отчёты:** фоновые задания с ограничением ресурсов, таймаутами и отдельным пулом worker; результат хранит фильтры, версию формулы, время и обработанную границу данных. UI опрашивает состояние задания, а не удерживает долгий HTTP-запрос.
4. **Рост:** отдельные вычислительные ресурсы и, при измеренной необходимости, аналитическая БД. Один из вариантов — ClickHouse для OLAP; добавление определяется объёмом и профилем запросов, а не включается в MVP заранее. [Назначение ClickHouse](https://clickhouse.com/docs/get-started/about/intro).

Для согласованного многошагового отчёта выбирается один снимок данных: например, read-only транзакция REPEATABLE READ. Несколько независимых запросов с текущими данными могут дать несогласованные числитель и знаменатель. [Уровни изоляции PostgreSQL](https://www.postgresql.org/docs/current/sql-set-transaction.html).

Свежесть витрины показывается пользователю; её обработанная граница должна означать полностью обработанный набор событий, а не просто максимальный выданный ID. Пересчёт на исправленных данных не скрывает версию определения метрики. Старый выгруженный отчёт сохраняет сведения о моменте расчёта.

Тяжёлые расчёты не должны вытеснять сохранение отметок. Сначала выделяются пул подключений, ограничение времени и параллельности; при необходимости worker и аналитические данные выносятся на отдельный узел. Копия для чтения с задержкой не гарантирует актуальные права: они перепроверяются в основной системе.

## Доступ к агрегатам

Область чтения определяется текущими правами до агрегации. Кэш ключуется пользователем/разрешённой областью, фильтрами, версией формулы/дерева тем и свежестью данных; отзыв доступа инвалидирует либо делает недоступными старые результаты.

Перед запуском фонового отчёта и перед скачиванием проверяются права. Если область сузилась, старый файл с более широкими данными не выдаётся: отчёт пересчитывается или отклоняется. Общесервисный процент не показывается роли, которой запрещены составляющие кружки.

## Векторный поиск и возможный перенос

Векторный слой закладывается для похожих задач, семантического поиска и рекомендаций. Учёт пользователей, ролей, выдач, участия и точных результатов остаётся в PostgreSQL. Перенос всего учёта в векторное хранилище не является требованием для добавления такого поиска.

Первый вариант — pgvector в PostgreSQL: он поддерживает точный и приближённый поиск соседей, в том числе индексы HNSW. Приближённый поиск и фильтры требуют оценки полноты результатов; его нельзя использовать для точного подсчёта метрик. [Документация pgvector](https://github.com/pgvector/pgvector).

Для последующего выделения отдельного векторного движка предусматривается интерфейс поиска по стабильным ID материала. Основные операции — индексировать, удалить и найти кандидатов; metadata модели и подготовки текста хранятся независимо от конкретного хранилища. Backend перепроверяет текущие права и доступность найденных объектов.

Индекс обновляется через фоновые события после публикации/архивации. Ошибка индексации не отменяет выдачу листка или отметку. Повторная индексация идемпотентна по ID материала, виду текста, версии модели и хешу исходника. Модель, размерность и способ подготовки текста версионируются; замена модели создаёт новый индекс с проверкой качества перед переключением.

Условия и решения индексируются отдельно по аудиториям. В частности, ответ школьнику не может содержать текст скрытого решения или сниппет из закрытого индекса; разрешение на открытое решение проверяется по текущему кружку и участию. Права проверяются и на этапе поиска кандидатов, и перед выдачей результата. Получение слишком малого числа допустимых кандидатов решается повторным ограниченным поиском, а не отключением фильтра доступа.

Перенос движка: построить новый индекс из исходных материалов → догнать события → сравнить качество и задержку на тестовом наборе с формулами → переключить адаптер → сохранить возможность возврата. Векторные расстояния и качество поиска не считаются одинаковыми между разными моделями/движками.

Векторы воспроизводимы только при наличии исходников, конкретной модели/доступа к ней и версии подготовки. Поэтому в полные копии входят и существующие векторы/снимки, и сведения о воспроизведении; длительность перестройки учитывается в цели восстановления. Без необходимости персональные данные детей в embeddings не включаются.

## Текущая локальная демка

Уже считаются уникальные назначенные и решённые пары, закрытие по задаче и всему разрешённому срезу, фильтры кружка и темы с потомками. Личная история школьника сохраняется после выбытия; чужие результаты доступны ему только как журнал текущего кружка. Несколько ролей не расширяют область групповой аналитики.

Для небольших демоданных дедупликация пока выполняется Python-множествами. Перед размещением на 100 кружков её нужно перенести в SQL, добавить пагинацию, нагрузочный сценарий, временные фильтры, экспорт и worker. Исторические метрики, версионированные задания, витрины, pgvector и OLAP пока спроектированы, но не реализованы. Все будущие вычислительные ресурсы и модели разворачиваются в России.


## Фильтры локальной демки

Реализованы город кружка, конкретный доступный кружок, тема задачи с потомками, теги задач и теги листков. Фильтры разных измерений соединяются через И: город и кружок ограничивают источники назначений, тег листка ограничивает назначения листков, тег и тема задачи — фактические задачи расчёта. Другие задачи того же листка не попадают в метрику только потому, что одна из задач совпала с фильтром. Общая решённость и удаление дублей школьник × задача сохраняются.

API: `/api/analytics?city=Москва&problem_tag=ID&worksheet_tag=ID&topic=UUID&circle=UUID`. Несколько ID одного типа через запятую означают ИЛИ внутри измерения. Тег другого типа или некорректный ID отклоняется. Архивные теги доступны для исторических срезов. Школьник по-прежнему получает только личную аналитику, включая собственные назначения после выхода из кружка; город фильтрует и эту историю.

Такие же фильтры поддержаны в `/api/circles?city=...`, `/api/materials/problem?tag=...`, `/api/materials/worksheet?tag=...` и `/api/circles/UUID/issues?tag=...`. Фильтр применяется после ограничения прав и перед ограничением числа материалов. Справочники городов интерфейс получает только из разрешённых кружков. Темам теги не назначаются.


## Подробный отчёт локальной демки

Вкладки: обзор, задачи, листки, темы, школьники и кружки. Последние две доступны только при групповой аналитике. Все таблицы имеют поиск, сортировку и страницы по 20 строк; фильтры города/кружка/темы/тегов общие для всех вкладок. Обзор содержит распределение прогресса, медиану, темы, задания с меньшим закрытием и покрытие разбора.

Дополнительные определения:

- Получатели — школьники хотя бы с одной назначенной задачей выбранного среза, включая выбывших. Школьники без назначений не входят в знаменатели. «Без решённых задач» означает ноль текущих да в этом срезе, а не отсутствие активности или посещаемости.
- Индивидуальный прогресс — решённые уникальные задачи школьника / его уникальные назначенные задачи. Медиана вычисляется по неокруглённым индивидуальным процентам; общий процент взвешен числом задач, поэтому может отличаться от медианы.
- Распределение: ровно 0%; больше 0 и меньше 25%; от 25 до 50%; от 50 до 75%; от 75 до 100%; ровно 100%. Промежуточные верхние границы не включаются. Один получатель входит в один диапазон.
- Полностью закрытые листки — уникальные пары школьник × опубликованный листок, у которых решены **все задачи полного состава**. Повторная выдача того же листка в другом кружке не создаёт вторую такую пару. Фильтр задачи/темы ограничивает прогресс строки, но не упрощает условие полного закрытия. В знаменатель входят получатели листков, содержащих хотя бы одну задачу выбранного среза.
- По теме считаются задачи узла и потомков текущего дерева. Одновременная привязка задачи к родителю и потомку не даёт дубль в родителе. Разные ветки могут пересекаться; их суммы не становятся общим итогом.
- По кружку задачи дедуплицируются внутри кружка; одна глобальная решённая задача может входить в несколько строк кружков. Разбор считается отдельно для каждого кружка × задачи, назначенной получателям среза. Открытое решение — отдельная характеристика разбора. Метрика «После разбора есть нерешившие» считает уникальные задачи, для которых в хотя бы одном разрешённом кружке остался нерешивший получатель.
- Результаты по ученикам не содержат email; класс вычисляется на текущую дату. Исторический класс на дату выдачи пока не фиксируется.

Расчёт вынесен в `backend/core/analytics.py`. Сначала ограничивается доступ, затем применяются фильтры. Результаты, разборы, составы и темы загружаются пакетно; внутри циклов получателей нет отдельных запросов БД. Агрегации строятся по множествам уникальных пар. Перенос больших срезов в SQL-витрины/фоновые задания остаётся этапом подготовки рабочей мощности.

Школьник получает только свои агрегаты, темы и листки, в том числе личную историю после выхода. Именные таблицы школьников, строки кружков, групповое распределение и разборы ему не возвращаются. При совмещении ролей сведения о сверстниках берутся только из кружков с действующим групповым доступом; круги с личным доступом не расширяют его. Аналитику нельзя использовать для чтения условий или решений задач.

Это состояние на момент расчёта за всё время. Посещаемость, время работы и историческая кривая обучения не выводятся: необходимых фактов для них пока нет. Низкое закрытие само по себе не доказывает сложность задания или качество преподавания; рядом показан размер выборки.


Интерфейс фильтра тем поддерживает дерево и несколько выбранных веток. В API они передаются повторяющимся параметром `topic` (старый формат через запятую тоже поддержан); сервер объединяет узлы и их потомков, затем дедуплицирует задачи и пары школьник × задача. Одновременный выбор родителя, потомка и повторяющегося ID не меняет метрики. Пустой выбор снимает фильтр тем. Нажатие на раздел графика сохраняет прежнее действие: показать только эту ветку; в дереве затем можно добавить другие.


Все фильтры отчёта допускают несколько значений. UI передаёт `city`, `circle`, `problem_tag`, `worksheet_tag` и `topic` повторяющимися параметрами, например `?city=Москва&city=Казань&circle=UUID1&circle=UUID2`. Повторяющиеся теги и ID также могут передаваться через запятую для обратной совместимости. Названия городов не делятся по запятой: это часть названия, а не разделитель. Город нормализуется обрезкой пробелов с обеих сторон.

Значения внутри фильтра объединяются по «или», разные фильтры пересекаются по «и». Все выбранные кружки сначала проверяются на чтение; наличие хотя бы одного недоступного кружка возвращает 404, даже если город исключил бы его из результата. Некорректный ID возвращает 400. При фильтрации городами сохраняется личная история школьника после выхода; выбор конкретных кружков по-прежнему требует действующего доступа. Ни объединение кружков, ни повторяющиеся значения не расширяют разрешённую область и не удваивают глобальные пары школьник × задача.
