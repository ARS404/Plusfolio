# Общее дерево тем

У задач и листков один общий справочник тем. Каждый опубликованный материал имеет одну или несколько тем; один узел дерева может быть выбран и у задачи, и у листка. Три отдельных справочника тегов продолжают описывать дополнительные признаки своих типов объектов.

## Референс problems.ru

На problems.ru каталог раскрывается от общего раздела к подтемам и показывает путь до текущего раздела: например, «Геометрия → Планиметрия → Треугольники». В разделе доступны его подтемы и список задач. [Каталог планиметрии](https://problems.ru/view_by_subject_new.php?parent=195).

Одна задача может иметь несколько тематических привязок: у задачи 55374 указаны «Пятиугольники» и «Векторы помогают решить задачу». [Карточка задачи](https://problems.ru/view_problem_details_new.php?id=55374).

Для Plusfolio приняты общий иерархический каталог, путь к теме, несколько тематических привязок материала и просмотр ветки целиком. По требованию проекта сама иерархия — строго дерево: у узла один родитель. Совместное использование темы разными материалами не создаёт второго родителя у темы.

## Структура и правила

Пример организации разделов, без фиксации полного начального справочника:

```text
Все темы
├── Геометрия
│   ├── Планиметрия
│   │   ├── Треугольники
│   │   │   └── Прочее
│   │   ├── Окружности
│   │   │   └── Прочее
│   │   └── Прочее
│   ├── Стереометрия
│   │   └── Прочее
│   └── Прочее
├── Методы
│   ├── Индукция
│   │   └── Прочее
│   ├── Инварианты
│   │   └── Прочее
│   └── Прочее
└── Прочее
```

Технический корень «Все темы» единственный, не назначается материалу, не удаляется и не архивируется. Глубина дерева не фиксируется числом уровней. Каждый другой узел имеет ровно одного родителя и достижим из корня; циклы и перенос узла внутрь собственной ветки запрещены.

Выбирать можно любой активный содержательный узел, в том числе имеющий подтемы. Это позволяет назначить листку широкую тему, а задаче — конкретную. Черновик может быть без тем; публикация требует хотя бы одной темы, и все выбранные темы должны быть доступны для нового назначения. Повтор одной и той же связи запрещён.

Темы листка задаются явно и не вычисляются автоматически из его задач. Для аналитики различаются «задачи выбранной темы» и «задачи из листков выбранной темы»: тематический листок может содержать вводные задачи других разделов.

## Прочее на каждом уровне

У корня и у каждой обычной темы автоматически есть ровно одна дочерняя тема «Прочее». Она создаётся вместе с разделом, в том числе если у него пока нет других подтем. Сама «Прочее» — конечный узел без детей: вложенное «Прочее → Прочее» не создаётся.

Это отдельные темы с разными ID: «Геометрия → Прочее», «Геометрия → Планиметрия → Прочее» и корневая «Все темы → Прочее» относятся к своим разделам. Их можно выбирать для задач и листков на общих основаниях. Привязка явная: отсутствие темы не заменяется автоматически на «Прочее».

Тема помечена `is_other=true`, имеет стабильный уникальный код и отображается последней среди детей родителя. Название «Прочее» зарезервировано для системных узлов, поэтому обычная тема с таким же названием не создаёт дубль. Поиск показывает полный путь, чтобы одноимённые темы не путались. Учитель выбирает её как готовую тему; администратор управляет её родительским разделом.

Системную «Прочее» нельзя отдельно переименовать, переместить, удалить или архивировать, а под ней нельзя создать потомка. При переносе раздела она следует за ним с сохранением ID; при архивации родителя становится недоступна для новых назначений вместе с веткой. Операции создания/импорта дерева идемпотентно обеспечивают наличие одной такой темы под каждым обычным узлом и корнем.

## Управление и неизменяемость

Администратор создаёт и переименовывает обычные темы, выбирает родителя, меняет порядок и архивирует ветки. Системные темы «Прочее» сопровождают родительские разделы по правилам выше. Учитель выбирает готовые темы своих черновиков задач и листков. Темы не меняют права доступа аналитика: они по-прежнему определяются тегами кружков.

После публикации набор topic_id материала фиксируется вместе с его содержимым. Для изменения этого набора создаётся копия материала. Переименование темы или перенос её ветки сохраняет topic_id и не переписывает материал, но может изменить путь и группировку в текущей аналитике.

Каждое административное изменение сохраняет неизменяемую версию каталога с ID, родителями, названиями, порядком и архивностью узлов. Публикация фиксирует версию каталога на этот момент; отчёт сохраняет использованную версию, чтобы перегруппировка не делала старые результаты невоспроизводимыми.

Архивный узел и его потомки недоступны для новых назначений, но старые привязки читаются и могут участвовать в исторических фильтрах. Для удаления из активного справочника используется архивация с сохранением ID и истории. Существующие материалы не теряют классификацию при архивации темы.

## Поиск и аналитика

- По умолчанию выбор темы включает сам узел и всех его потомков. Отдельный режим «только эта тема» ограничивает поиск прямыми привязками.
- Несколько выбранных веток объединяются по ИЛИ. Дополнительные теги и другие фильтры сужают результат по И.
- Объект с двумя подходящими темами появляется в выдаче один раз. Одновременный выбор родителя и дочерней темы также не дублирует результат.
- Для процента закрытия по теме сначала выбираются подходящие задачи, затем считаются уникальные назначенные и решённые пары школьник × задача в разрешённом срезе.
- Процент родительского раздела вычисляется по его уникальным фактам, а не средним процентов подтем. Строки разных тем могут пересекаться.
- «Прочее» включает только материалы с явной привязкой к этому узлу. Это не вычисляемая разность между родителем и остальными подтемами; добавление новой подтемы не переклассифицирует прежние материалы.
- Счётчики задач/листков и агрегаты учитывают права роли. Общедоступное чтение структуры справочника не открывает закрытые материалы или решения.

## Хранение и интерфейс

Основной вариант PostgreSQL — `Topic` с parent_id и отдельные связи `ProblemTopic`/`WorksheetTopic`. Потомки и путь выбираются рекурсивными запросами; PostgreSQL поддерживает такую работу с деревьями. [Рекурсивные запросы PostgreSQL](https://www.postgresql.org/docs/current/queries-with.html#QUERIES-WITH-RECURSIVE). При измеренной необходимости можно добавить производный кэш связей предок–потомок.

Изменения дерева сериализуются в транзакции с обновлением версии каталога: две одновременные операции не должны образовать цикл. Ограничения структуры проверяются сервером; внешнего ключа parent_id самого по себе недостаточно.

В редакторах задач и листков нужен общий выбор нескольких тем с раскрытием веток и поиском по названию/пути. Карточка показывает выбранные темы и их путь. В банке — фильтр по дереву, счётчики в разрешённом срезе и навигационный путь. Это точечное дополнение требований; общий визуальный редизайн остаётся следующим этапом.

## Проверки реализации

Общие topic_id у задачи и листка; минимум одна тема при публикации; несколько тем на объект; запрет второго родителя, цикла и переноса корня; перенос ветки с сохранением ID; архивация родителя; фильтр с потомками и без них; дедупликация пересекающихся веток; воспроизводимость отчёта по версии каталога; отсутствие закрытых данных в счётчиках и поиске. Отдельно: одна «Прочее» у каждого обычного узла и корня, отсутствие «Прочее» внутри «Прочее», идемпотентное создание, запрет изменения системного узла отдельно от родителя и различение одноимённых узлов по пути.

## Начальный импорт и происхождение

По решению пользователя начальное дерево копируется из математического каталога problems.ru (корень 1302). Самостоятельные внешние каталоги, например информатика, в этот математический импорт не входят. Сборщик получает только названия, связи и стабильные исходные ID через публичный выбор темы. Условия, решения, счётчики задач и персональные данные не копируются. Источник каждого узла и все посещённые страницы перечислены в JSON-снимке.

В исходнике терминальные темы вида «… (прочее)» нормализуются в системную «Прочее» своего родителя с сохранением исходного имени/ID в данных происхождения. Где такого узла нет, он добавляется. ID системной темы стабилен по родителю, поэтому продолжение импорта не меняет существующие привязки.

Снимок `data/problems_topics.json` содержит исходные узлы и рёбра, нормализованное дерево, отчёт о конфликтах и признак полноты. `metadata.complete=true` означает, что раскрыты все достижимые ветки математического корня. До этого интерфейс показывает незавершённость. Сборщик соблюдает robots.txt, задержку не меньше 20 секунд, использует локальный кэш и сохраняет прогресс после каждой страницы.

Импорт в БД идемпотентен по стабильным UUID от исходных ID: добавляет недостающие узлы, но не перезаписывает правки администратора. Конфликт источника с несколькими родителями или циклом фиксируется отдельно и блокирует импорт до явного разрешения. Команды продолжения и загрузки — в [README](../README.md).

Полный начальный импорт проверен 21.10.2026: **998 исходных узлов** математического дерева, **1 684 узла** после нормализации, включая технический корень и **842 системные «Прочее»**. Все 160 достижимых веток раскрыты; конфликтов и ошибок загрузки нет. Копируются только темы.

## Темы импортируемых задач

Отдельный импорт задач описан в [problems-import.md](problems-import.md). Он сопоставляет темы по исходным ID, сохраняет ручные переименования/переносы и может создать отсутствующие узлы из сохранённого дерева вместе с «Прочее». Импорт самой структуры по-прежнему не загружает тексты задач.
