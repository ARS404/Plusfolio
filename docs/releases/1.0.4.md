# Plusfolio 1.0.4

Релиз от 02.11.2026: версия `1.0.4`, статус `released`, неизменяемый тег `v1.0.4`. Состав изменений — в [CHANGELOG](../../CHANGELOG.md), результаты проверки перед релизным коммитом — в [отчёте](1.0.4-checks.json).

## Что изменилось

- Компактный журнал с короткой сводкой школьника, закреплёнными именами и сохранением положения таблицы при отметках.
- Прогресс каждой задачи «решили / получили» для взрослых по выбранным выдачам и текущему поиску школьников. Получатели повторяющейся задачи учитываются один раз; учитываются только существующие назначения.
- Страницы школьников, открываемые по имени из журнала, участников и общей аналитики: ФИО, ID, класс, год выпуска, доступные кружки, число выданных листков и периоды участия.
- Индивидуальный отчёт с обычными фильтрами и галочкой учёта разобранных задач. Все показатели ограничены назначениями выбранного школьника и областью группового доступа читателя. Преподаватель видит свои кружки, аналитик — область тегов, администратор — всех школьников, включая ещё не зачисленных. Роль школьника сама по себе доступа к этим страницам не даёт; личные кружки совмещённой роли не расширяют просмотр чужих данных. Контакты не возвращаются.
- Новые GET-методы `/api/v1/students/{student_id}` и `/api/v1/students/{student_id}/analytics`, метаданные `recipient_ids` в блоках журнала только при `show_group_stats=true`. Справка сайта и OpenAPI актуализированы.
- Меньше повторных вычислений и объектов в расчётах, потоковая история участия, отдельный кэшируемый пакет KaTeX. Вёрстка карточки участия и подписи исправлены на широком и узком экранах.

[Локальные замеры уборки](../benchmarks/cleanup-student-profiles-2026-11-02.json) описывают синтетические наборы, выделения памяти Python и отдельные функции. Они не являются нагрузочной проверкой сервера. Основной JS-файл после разделения сборки — около 380 КБ, математический — около 261 КБ; оба загружаются при старте, библиотека может кэшироваться отдельно.

## Данные и совместимость с 1.0.3

Новых миграций нет. Последняя миграция — `0019_issue_edit_version`, уже входящая в 1.0.3. Модели, зависимости, версия API `/api/v1`, модель поиска и шаблоны TeX не меняются. Устанавливать отдельный SQL-скрипт, заново назначать листки или сбрасывать кэши не нужно.

`server.py update` сохраняет БД и volumes. После свежей резервной копии контейнер `initialize` выполняет штатный `migrate --noinput`: уже применённые миграции не запускаются повторно. Сохраняются UUID, номера, листки и их редакции, выдачи, назначения, изображения, плюсы, разборы и настройки. При обновлении сразу с более старой версии Django применит недостающие миграции по порядку; условия перехода описаны в [1.0.3](1.0.3.md) и [серверной инструкции](../server-deploy.md).

## Проверка перед выпуском

```bash
python3 scripts/release.py --check
python3 scripts/release.py --check-tag v1.0.4
.venv/bin/python backend/manage.py makemigrations --check --dry-run
.venv/bin/python backend/manage.py migrate --plan
.venv/bin/python backend/manage.py test core.test_release core.test_student_profiles core.test_api_reference core.test_block_migration --noinput
PYTHONPATH=deploy .venv/bin/python -m unittest deploy.test_shared_host deploy.test_capacity deploy.test_cloud_deploy.ImageTests deploy.test_downloads
(cd frontend && npm test && npm run build)
git diff --check
```

При подготовке используется отдельная тестовая БД. Полная локальная регрессия после уборки: 372 backend-теста прошли, 4 PostgreSQL-проверки пропущены. На релизном номере повторно проверяются идентичность версии, права и отчёты школьников, контракт API, сохранение данных при прежних миграциях и серверные утилиты. После смены номера заново собирается frontend. Linux/Docker и PostgreSQL проверяются отдельно в CI; их результат не подменяется локальными SQLite-тестами.

## Установка опубликованного релиза

В чистой папке исходников действующего экземпляра, сохранив ключ `.deploy/backup.key` отдельно:

```bash
python3 scripts/server.py backup
git fetch origin --tags
git switch --detach v1.0.4
python3 scripts/server.py update
python3 scripts/server.py version
python3 scripts/server.py check-public
```

Для готовых образов вместо обычного `update`: `python3 scripts/server.py update --release /путь/images-1.0.4.json`. Манифест должен соответствовать версии и архитектуре сервера. Отдельная предварительная копия проверяет доступность резервирования; сам `update` создаёт ещё одну свежую полную копию после остановки пишущих `web`, `mail` и `indexer`. Не заменяйте его командой `up` при смене версии.

Проверки после установки:

1. `version` и `/healthz` сообщают `1.0.4` и ожидаемую ревизию; внешний `check-public` проходит.
2. Прежний журнал, назначения и отметки сохранены. Строки компактны, прогресс задачи меняется при поиске школьника и выборе выдач; повтор задачи не удваивает получателя.
3. Преподаватель, аналитик и администратор открывают доступные им страницы школьников. Даты обозначают участие, счётчик — полученные выдачи. Закрытые кружки и контакты не появляются.
4. Личный отчёт содержит только выбранного школьника; фильтры и оба положения галочки учёта разобранных работают. Школьник видит только собственные итоги и личную аналитику, профили сверстников ему недоступны.
5. Условия с формулами и PDF открываются; доверенные ресурсы TeX остаются прогретыми.

## При сбое

При ошибке резервной копии `update` возобновляет прежние контейнеры без изменения схемы. При ошибке инициализации зависимые службы не запускаются: проверьте `python3 scripts/server.py logs initialize`, устраните причину и повторите обновление. Автоматического отката нет. Восстанавливайте согласованный комплект приложения и БД из бэкапа; [полная процедура восстановления](../server-deploy.md).
