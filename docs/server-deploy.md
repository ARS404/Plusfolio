# Серверная установка Plusfolio

Это запуск реального сервиса без демонстрационных аккаунтов: PostgreSQL/pgvector, HTTPS, CPU-модель и индексатор, изолированный Tectonic, очередь SMTP-приглашений и зашифрованные резервные копии. Сервисы запускаются и восстанавливаются после перезагрузки через Docker Compose. Хост — Linux amd64 или arm64; подготовку проверяет `deploy/check_server.py` на синтетических данных.

## Первый запуск: скопировать код и запустить установщик

Для сервера в России с Debian 12 / Ubuntu 24.04:

```bash
git clone git@github.com:ARS404/Plusfolio.git
sudo bash Plusfolio/scripts/install_server.sh
```

Если GitHub-репозиторий закрыт, для клонирования нужен доступ на чтение либо передача архива исходников на сервер. Не переносите личный SSH-ключ на сервер: используйте отдельный read-only deploy key или архив. Если Docker, Compose и Python 3 уже установлены, можно сразу запустить `python3 scripts/server.py init` из папки проекта без установки системных пакетов.

Установщик спрашивает только внешние параметры:

- HTTPS-адрес сайта. Домен должен указывать на этот сервер, входящие TCP 80 и 443 — быть доступны.
- Email, имя и пароль первого администратора (не менее 12 символов).
- SMTP-хост, порт, логин, пароль и адрес отправителя. Для 587 используется STARTTLS, для 465 — SSL. SPF/DKIM/DMARC настраиваются у владельца домена по инструкции почтового провайдера.

Пароли вводятся скрыто. Приложение и БД получают отдельные случайные ключи. Все параметры остаются в `.deploy/`, исключённой из Git и контекста Docker-сборки. Каталог доступен только владельцу. Первый администратор создаётся только в пустой БД. Его пароль применяется **только при создании**: повторный запуск не сбрасывает пароль и не повышает роль существующего обычного пользователя.

Далее автоматически собираются интерфейс и образы, скачиваются проверенные Tectonic/модель, прогреваются ресурсы TeX, создаются БД/расширения, применяются миграции, импортируется дерево тем, запускаются службы и проверяются HTTPS, SMTP и готовность приложения. Тест SMTP устанавливает соединение и проверяет авторизацию, не отправляя письмо. Пользовательские задачи, листки и школьники при установке не импортируются; исходный каталог тем входит в Git.

Первый запуск скачивает зависимости и образы и поэтому зависит от сети. Последующие запуски используют готовые образы. Для полностью автономного переноса можно сохранить образы командой `export-images` и загрузить их через `docker image load`; архитектура образов должна совпадать с сервером. Рабочие персональные данные и inference остаются на выбранном российском сервере. Для сертификата и почты используются указанные внешние службы; скачивание моделей происходит во время подготовки образа, не при пользовательском запросе.

Если установка выполнялась через sudo, управляйте экземпляром из root-сессии или добавляйте sudo перед командами ниже.

## Повторный запуск и обновление

```bash
python3 scripts/server.py up
python3 scripts/server.py status
python3 scripts/server.py logs web mail indexer backup
```

После обновления исходников:

```bash
python3 scripts/server.py backup
git pull --ff-only
python3 scripts/server.py update
```

`up` не переустанавливает зависимости. `update` пересобирает изменившиеся образы и применяет миграции. При ошибке команда завершается ненулевым кодом и не объявляет сервис готовым. Повторный запуск не удаляет данные. Не запускайте `docker compose down --volumes` на рабочем экземпляре: это команда удаления хранилищ, она используется только для одноразовых тестов.

Чтобы изменить SMTP или домен, исправьте соответствующие несекретные поля `.deploy/env` и секрет `.deploy/secrets/smtp_password` (сам пароль не помещайте в env/командную строку), затем запустите `up`. Настройки origin, Secure cookies, ссылки инвайтов и HTTPS берутся из одного PUBLIC_URL. После смены домена настройте DNS и проверьте готовность.

## Приглашения

Войдите администратором, создайте кружок и отправьте приглашение преподавателю. Преподаватель затем приглашает школьников. Письмо уходит через SMTP в фоне и содержит ссылку именно на PUBLIC_URL. В «Приглашениях» отдельно видны состояние доступа и отправка письма: очередь, повтор, отправлено, ошибка или отмена.

Временные ошибки получают до восьми попыток с увеличивающейся задержкой. Отозванные, истёкшие приглашения и приглашения отправителя, потерявшего право выдавать доступ, не отправляются. При окончательной ошибке проверьте адрес/SMTP и создайте новое приглашение. Локальный просмотр писем и кнопки демо-профилей на сервере выключены.

SMTP не даёт универсальной гарантии exactly-once: если провайдер принял письмо, а процесс остановился до записи статуса в БД, возможен повтор с тем же Message-ID. Повторное принятие инвайта не создаёт второй аккаунт или второе участие. Текст письма, токен, SMTP-пароль и ответ провайдера не записываются в служебные логи.

## Изоляция TeX

Веб-контейнер не получает Docker socket или привилегий. Компиляция работает отдельно через Unix-сокет: контейнер без сети, без БД/ключей/SMTP, read-only rootfs, cap_drop=ALL, no-new-privileges, лимиты памяти, процессов, CPU, размера файлов и 20 секунд на задание. Одновременно выполняется одно задание, его временные файлы удаляются. Аргументы, Tectonic 0.17.0, шаблон, TikZ и offline-ресурсы совпадают с пакетом предпросмотра для роботов. Привилегированный режим и отключение seccomp не требуются.

PostgreSQL, Redis, модель и компилятор не публикуют TCP-порты наружу. Публичный вход — Caddy с HTTPS; выдача материалов и решений всегда проверяет права в Django. Общий Redis обслуживает ограничения запросов нескольких веб-процессов.

## Резервные копии и восстановление

Сразу после установки и далее каждые 24 часа создаётся зашифрованный age-комплект в отдельном Docker volume `backups`. В него входят согласованный `pg_dump`, исходники/миграции, собранный frontend, конфигурация и ключи приложения/SMTP/БД, Tectonic и подготовленные ресурсы, файлы модели и SHA-256-манифест. PDF-кэш пересобирается и не сохраняется. Приватный ключ `.deploy/backup.key` в архив **не входит**.

Сохраните `.deploy/backup.key` вне сервера и отдельно от файлов бэкапа. Без него копия не расшифруется. Сама копия на том же сервере не защищает от потери сервера; выгружайте её в отдельное российское хранилище. Адрес и доступ к внешнему хранилищу нельзя создать автоматически без аккаунта владельца. Политика внешних копий/PITR — в [плане резервирования](backups.md); ежедневный комплект не является непрерывным WAL/PITR и не обещает RPO 15 минут.

```bash
python3 scripts/server.py backup
python3 scripts/server.py download-backup ./saved-backups
python3 scripts/server.py verify-backup ./saved-backups/plusfolio-ДАТА.tar.gz.age --key /secure/backup.key
python3 scripts/server.py export-images ./plusfolio-images.tar
```

`verify-backup` расшифровывает архив во временном каталоге, проверяет структуру и все SHA-256; БД при этом не меняется. Для автономного восстановления сохраняйте образы соответствующего релиза и архитектуры отдельно от хоста. `.deploy/image-lock.json` фиксирует ID запущенных образов.

Автоматическое восстановление создаёт новую папку и отдельный Compose project, проверяет весь архив и не перезаписывает существующий экземпляр:

```bash
# На новом сервере сначала загрузите ранее сохранённые образы:
docker image load --input ./plusfolio-images.tar
python3 scripts/server.py restore-backup ./saved-backups/plusfolio-ДАТА.tar.gz.age --key /secure/backup.key --into /opt/plusfolio-restored
cd /opt/plusfolio-restored/source
python3 scripts/server.py restore-database /opt/plusfolio-restored/database.dump
python3 scripts/server.py up
```

Для восстановления нужны новая установка/пустые volumes, архив и приватный ключ. Нельзя накатывать архив поверх работающего сервиса. Порядок: расшифровать и проверить комплект; восстановить конфигурацию/ключ приложения; запустить новую БД с её отдельным паролем; загрузить database.dump через `pg_restore`; восстановить модель/TeX; отозвать прежние сессии, API-токены и незавершённые приглашения/почтовую очередь; проверить вход, роли, выдачу листка, CPU-поиск и PDF. Скрипт проверки установки отдельно проверяет архив; процедуру восстановления БД проверяют интеграционные тесты на отдельной БД, а не на рабочем экземпляре.

## Воспроизводимая проверка

```bash
python3 deploy/check_server.py
```

Запускайте из чистой копии без рабочей `.deploy`. Тест создаёт отдельный Compose project, локальный HTTPS с собственной CA и одноразовый SMTP-приёмник без внешних адресатов. Запускает регрессионные тесты листков, API, поиска и SMTP в отдельной PostgreSQL test-БД. Проверяет создание администратора без демо-аккаунтов, задачи/листки, TikZ PDF с/без решений, отправку приглашения, регистрацию и автоматическое назначение листков, реальную CPU-модель, OpenAPI, перезапуск служб и целостность зашифрованного бэкапа. После теста удаляются только созданные им volumes. `--keep` оставляет тестовый экземпляр для диагностики.

GitHub Actions запускает эту проверку на чистом Ubuntu amd64 при изменениях main/PR. Никакие рабочие секреты или данные ему не нужны. Официальные источники: [Docker Engine](https://docs.docker.com/engine/install/), [Compose](https://docs.docker.com/compose/), [pgvector](https://github.com/pgvector/pgvector), [Caddy](https://caddyserver.com/docs/automatic-https).
