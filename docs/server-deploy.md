# Plusfolio на общем сервере

Установщик использует готовые Docker Engine 28+, Compose v2, Buildx и Python 3. Он не устанавливает и не обновляет пакеты хоста, не перезапускает Docker/containerd, не вызывает команды настройки firewall и не меняет конфигурацию чужого прокси. Если зависимость отсутствует, доступ к Docker закрыт или cgroups не поддерживает обязательные лимиты, установка останавливается с объяснением. Подготовку системы выполняет её администратор.

Plusfolio публикует только HTTP на **127.0.0.1:18080**. Порт можно выбрать при установке. HTTPS и сертификаты остаются у существующего Nginx, Caddy или Traefik. PostgreSQL, Redis, CPU-модель и TeX наружу порты не публикуют. Docker создаёт штатные сетевые правила для своих сетей и опубликованного порта; общая конфигурация Docker не редактируется. Требование Docker 28+ связано с исправлением доступности loopback-портов со стороны соседей по сети в старых версиях: [port publishing](https://docs.docker.com/engine/network/port-publishing/).

## Первый запуск

На выбранном российском Linux-сервере с готовыми инструментами:

```bash
git clone git@github.com:ARS404/Plusfolio.git
bash Plusfolio/scripts/install_server.sh
```

Для закрытого репозитория нужен отдельный read-only deploy key либо передача архива исходников. Для запуска нужен существующий доступ пользователя к Docker. Скрипт сам не выдаёт доступ, не меняет группы пользователей и не вызывает sudo. При необходимости администратор может запустить его под подходящей учётной записью; файлы `.deploy` будут принадлежать этой записи.

Установщик спрашивает:

- Будущий внешний HTTPS-адрес сайта.
- Email, имя и пароль первого администратора.
- SMTP-хост/порт, логин, пароль и адрес отправителя приглашений.
- Локальный порт, по умолчанию 18080.

Пароли вводятся скрыто и хранятся в закрытом `.deploy/secrets`; каталог `.deploy` исключён из Git и Docker-контекста. До сборки проверяются занятость порта и принадлежность существующих контейнеров этому экземпляру. Чужой занятый порт не освобождается. Каждый новый экземпляр получает имя Compose project, зависящее от папки, и собственные имена образов. Переменная COMPOSE_PROJECT_NAME из окружения не может перенаправить команды на чужой проект.

Далее собираются образы в ограниченном сборщике, создаются собственные сети/volumes, применяются миграции и импортируется дерево тем. Первый администратор создаётся только в пустой БД; повторный запуск не меняет его пароль или роли. Демо-аккаунтов на сервере нет. Проверяются локальная готовность и соединение/авторизация SMTP. Письмо при этой SMTP-проверке не отправляется.

Сообщение `ready locally` означает готовность внутреннего приложения. Внешний HTTPS становится доступен после подключения существующего прокси. Для настройки прокси приложение уже может работать локально; сертификат не требуется для завершения установки. Первый запуск скачивает образы, модель и TeX-ресурсы. Прогрев TeX использует отдельный постоянный BuildKit cache mount: временный сетевой сбой не теряет уже скачанные пакеты; повторный init/update продолжает подготовку. При полном кэше сначала проверяется offline-сборка. Лимиты сборки намеренно уменьшают её влияние на соседей и могут увеличить время первого запуска.

## Повторная сборка

У каждого экземпляра остаётся собственный ограниченный BuildKit-сборщик; после сборки он останавливается. Его кэш сохраняет npm-пакеты, Python wheels, ONNX-модель и подготовленные TeX-ресурсы. Изменение исходников не переустанавливает зависимости. При изменении lock-файла подходящие wheels переиспользуются после проверки SHA-256; pip проверяет хеши и согласованность зависимостей. Кэш Python не смешивает пакеты разных платформ и не попадает в готовые образы.

При подготовке образа права на TeX-файлы назначаются в том же слое, где они создаются: изменение исходников приложения больше не добавляет повторную копию всего TeX-кэша. В runtime-образе не устанавливаются curl и полный набор GnuPG; загрузка ключа официального репозитория PostgreSQL использует HTTPS средствами Python, проверку APT-подписей выполняет APT.

Лимиты сборщика и политика его локальной очистки сохраняются: одна параллельная задача, целевой объём очистки кэша 2 ГБ с резервом свободного места. Это цель GC, а не дисковая квота: во время активной сборки объём может временно превышать её. Модель готовится в независимой стадии, поэтому изменение Python-зависимостей не меняет её ключ сборки. При достижении лимита BuildKit может удалить часть кэша; следующий запуск проверит и докачает недостающие ресурсы. Первый запуск требует доступа к реестрам пакетов и официальным ресурсам. Очистка кэша возможна без потери данных приложения и его резервных копий; глобальные команды Docker prune установщик не выполняет.

## Подключение существующего HTTPS-прокси

Получите пример под свой домен и выбранный порт:

```bash
python3 scripts/server.py proxy-config nginx
python3 scripts/server.py proxy-config caddy
python3 scripts/server.py proxy-config traefik
```

Команды только выводят текст. Изменение и проверку общей конфигурации выполняет администратор существующего прокси. Файлы `/etc/nginx`, общий Caddyfile и конфигурация Traefik установщиком не редактируются; чужие службы не перезагружаются.

Для Nginx пример добавляется в уже настроенный HTTPS server-блок домена. В нём обязательны исходный Host, `X-Forwarded-Proto: https` и корректный `X-Forwarded-For`. Нужен лимит тела запроса 8 МиБ и достаточный timeout для PDF. Для Caddy, работающего на хосте, достаточно отдельного сайта с `reverse_proxy 127.0.0.1:18080`.

Если существующий прокси работает в контейнере, его localhost относится к этому контейнеру. Администратор может подключить прокси к приватной сети `<имя-проекта>_frontend` и направить запросы на уникальный адрес `<имя-проекта>-web:8000`; имя видно в `.deploy/env`. Это отдельное осознанное действие администратора. Сети чужих контейнеров установщик не изменяет. Пример Traefik рассчитан на такое подключение и уже настроенный file provider/HTTPS entryPoint.

После подключения:

```bash
python3 scripts/server.py check-public
```

Проверка требует действующий сертификат и сверяет ID экземпляра: другой сайт, случайно открывшийся по домену, не считается успешным запуском. Для localhost в интеграционном тесте используется отдельная тестовая CA. Рабочие персональные данные и inference остаются на выбранном российском сервере. SMTP-провайдер и DNS/SPF/DKIM/DMARC настраиваются владельцем домена.

## Лимиты и диагностика

```bash
python3 scripts/server.py doctor
python3 scripts/server.py status
python3 scripts/server.py logs web mail indexer backup
```

`doctor` проверяет инструменты, cgroups, ограничения конфигурации, принадлежность проекта и порт без запуска/остановки служб. До первой настройки он проверяет инструменты и стандартный порт.

| Служба | CPU, верхняя граница | Память, верхняя граница |
| --- | ---: | ---: |
| Web | 0,30 | 512 МиБ |
| PostgreSQL | 0,30 | 512 МиБ |
| Redis | 0,05 | 128 МиБ |
| CPU-модель | 0,75 | 1 ГиБ |
| TeX | 0,30 | 512 МиБ |
| Индексатор | 0,15 | 256 МиБ |
| Приглашения | 0,05 | 192 МиБ |
| Бэкапы | 0,10 | 256 МиБ |

Проверки heartbeat не загружают Django/Redis SDK; для бэкапа используется быстрый уровень gzip, чтобы проверка здоровья и сжатие работали при небольшом CPU-бюджете.

Сумма верхних границ работающих служб: **2 CPU и 3392 МиБ памяти**. Это лимиты, а не постоянное потребление или резервирование. Одноразовая инициализация ограничена 0,50 CPU / 384 МиБ и завершается до запуска web/worker. Для всех служб задан лимит процессов и запрещён дополнительный swap сверх лимита памяти. Логи ротируются: до трёх файлов по 10 МБ на службу.

Изменять значения можно в `.deploy/env`: `WEB_CPUS`, `WEB_MEMORY`, `DB_CPUS`, `DB_MEMORY`, `REDIS_CPUS`, `REDIS_MEMORY`, `EMBEDDINGS_CPUS`, `EMBEDDINGS_MEMORY`, `TEX_CPUS`, `TEX_MEMORY`, `INDEXER_CPUS`, `INDEXER_MEMORY`, `MAIL_CPUS`, `MAIL_MEMORY`, `BACKUP_CPUS`, `BACKUP_MEMORY`. Затем выполните `up`. Бюджет нужно согласовать со свободными ресурсами общего сервера. CPU, диск и сеть физически остаются общими; контейнеры не дают гарантии нулевого влияния на задержки соседних приложений.

Сборщик BuildKit принадлежит этому экземпляру, по умолчанию ограничен **1 CPU / 1 ГиБ**, выполняет один шаг одновременно и останавливается после сборки. `BUILD_CPUS` и `BUILD_MEMORY` задаются в `.deploy/env`. Кэш сборщика очищается собственным GC с целевым объёмом 2 ГБ; общий builder пользователя не переключается, глобальные prune-команды не выполняются. При обновлении работающего экземпляра бюджет сборщика добавляется к бюджету служб: по умолчанию совокупные верхние границы составляют 3 CPU и 4416 МиБ. Скачивание и загрузка образов используют также Docker daemon; при очень тесном дисковом/сетевом бюджете лучше переносить готовые образы и обновляться в согласованное окно.

Проверка и восстановление архивов запускают временный helper с лимитом 0,25 CPU / 256 МиБ и доступом только к явно указанным файлам/выходной папке.

Для автономного переноса сохраните образы соответствующего релиза и архитектуры через `export-images`, затем загрузите их `docker image load`. `init --no-build` и `update --no-build` используют уже загруженные образы и не создают сборщик; имена образов должны совпадать с `.deploy/env`.

## Управление и обновление

```bash
python3 scripts/server.py up
python3 scripts/server.py backup
git pull --ff-only
python3 scripts/server.py update
python3 scripts/server.py stop
```

Команды ограничены сохранённым именем проекта и проверяют, что контейнеры с таким именем созданы из этой папки. Перенос папки действующей установки требует отдельной миграции, а не обхода проверки владельца. Чужие контейнеры, образы и volumes не удаляются. Никогда не выполняйте глобальные `docker system prune` или `docker volume prune` для обслуживания Plusfolio.

Если существующий экземпляр был установлен прежним вариантом с собственным Caddy на 80/443, `up` сохраняет БД/volumes/ключи и прежние имена образов, переводит web на локальный порт и останавливает только прежний proxy этого же проекта/папки. После этого нужно подключить существующий внешний HTTPS-прокси. Перед переходом сохраните бэкап и согласуйте переключение маршрута. При несовпадении владельца проекта переход останавливается.

## Приглашения

Администратор создаёт кружок и приглашает преподавателей; преподаватели приглашают школьников. SMTP-worker отправляет письма в фоне на внешний PUBLIC_URL. Состояния письма видны в интерфейсе отдельно от состояния доступа. Временные ошибки получают до восьми попыток, постоянные отказы прекращают отправку. Отозванные, истёкшие приглашения и приглашения отправителя, потерявшего права, не отправляются. SMTP допускает повтор письма после сбоя; одноразовая ссылка выдаёт доступ однократно. Подробнее — [доставка приглашений](email-delivery.md).

## Резервные копии и автоматическая очистка

Сразу после запуска и каждые 24 часа создаётся полный зашифрованный age-комплект: согласованный `pg_dump`, исходники/миграции, frontend, конфигурация/секреты, Tectonic и подготовленные ресурсы, модель и SHA-256-манифест. PDF-кэш пересобирается. Приватный `.deploy/backup.key` в архив не входит; сохраните его отдельно от сервера.

Политика по умолчанию:

- `BACKUP_RETENTION_DAYS=14` — срок хранения.
- `BACKUP_MAX_COUNT=14` — максимум архивов.
- `BACKUP_MAX_BYTES=2147483648` — целевой общий объём 2 ГиБ.
- `BACKUP_KEEP_MIN=2` — минимум последних успешных копий.

Очистка выполняется **после успешного создания новой копии**. Две последние копии сохраняются даже если они старше срока или вместе превышают целевой объём. Для больших БД увеличьте объём и предусмотрите место под очередной архив и временный dump: это политика хранения, а не файловая квота. Из-за минимального числа копий первые две копии могут занимать больше заданного объёма.

Удаляются только собственные обычные файлы с точным форматом имени `plusfolio-ДАТА.tar.gz.age` в volume `backups`. Символические ссылки и посторонние файлы не удаляются. Незавершённые собственные `.partial` старше суток очищаются. Общая блокировка исключает параллельные автоматическую/ручную копии и очистку; сбой создания новой копии не запускает удаление прежних успешных архивов.

```bash
python3 scripts/server.py backup
python3 scripts/server.py prune-backups
python3 scripts/server.py download-backup ./saved-backups
python3 scripts/server.py verify-backup ./saved-backups/plusfolio-ДАТА.tar.gz.age --key /secure/backup.key
python3 scripts/server.py export-images ./plusfolio-images.tar
```

Копии на том же сервере не защищают от его потери; выгружайте их в независимое российское хранилище. Ежедневный комплект не является WAL/PITR и не обещает RPO 15 минут. План внешних копий — [резервирование](backups.md).

## Восстановление

Нужны архив, приватный ключ и сохранённые образы нужной архитектуры. На новом сервере:

```bash
docker image load --input ./plusfolio-images.tar
python3 scripts/server.py restore-backup ./saved-backups/plusfolio-ДАТА.tar.gz.age --key /secure/backup.key --image ИМЯ_ОБРАЗА_APP --into /opt/plusfolio-restored
cd /opt/plusfolio-restored/source
python3 scripts/server.py restore-database /opt/plusfolio-restored/database.dump
python3 scripts/server.py up
```

Имя app-образа указано в `.deploy/env` исходного экземпляра и сохраняется в зашифрованной конфигурации/экспортированных тегах. `--image` позволяет расшифровать комплект на новом хосте без прежнего файла настроек. Источники восстанавливаются в новую закрытую папку; helper получает доступ только к ней и двум явно указанным файлам архива/ключа. Внутри сохраняются старые настройки SMTP и адрес сайта; выберите свободный LOCAL_PORT и подключите внешний прокси перед публичным запуском.

БД восстанавливается только в пустой экземпляр; прежние сессии, API-токены и незавершённые приглашения отзываются, неотправленные письма отменяются. Новое имя Compose project отделяет восстановление от исходного экземпляра. Существующий сервис/БД не перезаписываются. Вход/роли/выдачу листка/поиск/PDF нужно проверить до переключения рабочего домена.

## Проверка общего сервера

```bash
python3 deploy/test_shared_host.py
python3 deploy/check_server.py
```

Первая команда проверяет защиту чужого проекта/порта, отсутствие установки зависимостей, ограниченный сборщик и политику хранения. Вторая создаёт одноразовый экземпляр с тестовыми SMTP/HTTPS и отдельный соседний сайт с контрольными данными. Проверяет фактические Docker-лимиты, неизменность соседнего сайта при сборке/установке/перезапуске/остановке, PostgreSQL, приглашения, CPU-поиск, TikZ/PDF, очистку, архив и восстановление. Тестовые данные синтетические; рабочие секреты не нужны.

Источники по ограничениям: [Docker Compose services](https://docs.docker.com/reference/compose-file/services/), [ограниченный BuildKit builder](https://docs.docker.com/build/builders/drivers/docker-container/), [параллелизм BuildKit](https://docs.docker.com/build/buildkit/configure/).
