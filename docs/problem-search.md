# Локальный поиск по условиям и решениям

Модель: `intfloat/multilingual-e5-small`, 384 измерения, ONNX INT8. Закреплены revision и SHA-256 файлов в `embeddings/model.lock.json`; загружаются только ONNX и токенизатор, Python-код из модельного репозитория не выполняется. Один процесс ONNX Runtime использует только `CPUExecutionProvider`, по умолчанию два потока. Файлы занимают около 136 МБ (130 МиБ). Django не загружает модель и не требует PyTorch/CUDA.

## Быстрый локальный запуск

```bash
./scripts/run_demo.sh
```

Лаунчер устанавливает обычные зависимости, применяет миграции, собирает интерфейс и запускает приложение, CPU-модель и индексатор. ML-зависимости лежат в отдельном `.local/embedding-venv`; повторная установка пропускается при неизменном lock-файле. Загрузка модели выполняется только при отсутствии файлов или несовпадении SHA-256. При следующем запуске готовые векторы используются повторно.

Если приложение уже работает, запустите только поиск в другом терминале:

```bash
./scripts/run_search.sh
```

Не запускайте оба способа одновременно: порт 8011 занимает один процесс модели. Ctrl+C останавливает процессы, принадлежащие лаунчеру. `PLUSFOLIO_SEARCH=0 ./scripts/run_demo.sh` запускает приложение с текстовым поиском без модели. `EMBEDDING_THREADS=2` задаёт число потоков модели.

## Развёртывание рядом с существующим Django

1. Установите зависимости приложения из `requirements.lock`. PostgreSQL должен иметь расширения `vector` версии **0.8.0 или новее** и `pg_trgm`. В managed PostgreSQL включите расширения средствами провайдера до миграции; поддержка расширений обязательна. Миграция создаёт HNSW и GIN trigram индексы. SQLite используется только в демке и сканирует доступные векторы блоками на CPU.
2. Выполните обычный `python backend/manage.py migrate`.
3. Поднимите модель:

   ```bash
   docker compose -f compose.search.yml up -d --build
   ```

4. Для Django и индексатора задайте `PLUSFOLIO_EMBEDDING_URL=http://127.0.0.1:8011`. Если Django сам в контейнере, подключите сервисы к одной приватной docker-сети и используйте `http://embeddings:8011`.
5. Запустите `python backend/manage.py index_problem_search --watch` как отдельный процесс под systemd или другим уже используемым супервизором. Он использует те же переменные БД, что и Django. Для разовой индексации уберите `--watch`.

В Docker модель входит в собранный образ: при старте нет скачивания, токена Hugging Face или вызовов внешнего inference API. Подготовьте образ заранее и сохраните в российском registry либо перенесите через `docker save/load`. Зеркало базового образа и Python-пакетов тоже можно использовать при сборке. В рабочем российском контуре внешний доступ для поиска не нужен.

Порт модели опубликован **только на loopback**; наружу 8011 открывать нельзя. У сервиса нет пользовательской авторизации: доступ к нему разрешён только доверенным процессам на сервере/приватной сети. Compose ограничивает CPU двумя ядрами, RAM 2 ГБ, использует непривилегированного пользователя и файловую систему только для чтения. Контекст Docker исключает БД, ключи, `.local` и прочие файлы приложения. Docker-конфигурация подготовлена; на машине без Docker сборка контейнера не подтверждается локальными тестами Python.

## Индекс и доступ

- У каждой опубликованной задачи отдельные документы условия и решения. Обычный текст и TeX сохраняются для поиска; числа, регистр переменных и математические операторы не удаляются из точного сравнения.
- Новые документы создаются в той же транзакции, что и задача. Bulk-импорты подхватываются индексатором. Текстовый поиск доступен до расчёта эмбеддингов. Фоновый процесс идемпотентен; сбой модели откладывает повтор на минуту и не мешает сохранению задачи.
- Школьник ищет среди персонально назначенных задач. Закрытые решения исключаются из SQL-области **до** текстового и векторного поиска. Внешний top-k с последующим удалением запрещённых результатов не используется. Изменение ролей, выдач или показа решения действует без переиндексации.
- Выбор узла темы включает потомков; несколько тем/тегов объединяются так же, как в остальном сервисе. Поиск работает в банке, «Моих задачах», подборе задач в листок и проверке перед созданием.
- Векторизация покрывает весь документ: окна модели по 448 токенов с перекрытием, повторяемым E5-префиксом, mean pooling, нормализацией и объединением окон. Очень большие тексты отправляются ограниченными порциями; хвост решения не отбрасывается.
- Для гибридной выдачи используется reciprocal rank fusion текстовых и векторных кандидатов; точные совпадения стоят выше. Минимальная косинусная близость 0,73 — эвристика отбора кандидатов, **не** вероятность дубля. Числа и знаки проверяет человек. Материалы не объединяются автоматически.
- При недоступной модели возвращаются текстовые результаты и `notice`. `pending` считает только доступные документы выбранных полей. Никакие закрытые результаты не попадают в фрагменты.

## API

`POST /api/v1/problem-search` — операция чтения с JSON-телом, доступная также токену только для чтения. Для коротких запросов есть `GET` с теми же параметрами. Большие тексты передавайте через POST, чтобы не упираться в размер URL и не записывать условие в access-log.

```json
{"q":"вставленный текст задачи или решения", "field":"all", "scope":"library", "mode":"hybrid", "limit":20, "tag":[], "topic":[]}
```

`field`: `all`/`statement`/`solution`/`metadata` (название и описание); непустой массив `fields` позволяет выбрать несколько разделов; `scope`: `library`/`my`; аккаунт без teacher/analyst/admin ограничен `my`; при нескольких ролях доступ объединяется. `my` требует роли student. `mode=text` отключает модель. `q` до 12 000 символов; `limit` от 1 до 50; до 60 поисков в минуту на аккаунт в текущем Django cache. Для общего счётчика нескольких web-процессов требуется общий cache backend. `results` содержит материал и разрешённый фрагмент, `match` (`identifier`/`exact`/`text`/`semantic`), `fields`. `semantic` подтверждает использование модели в этом запросе. Форматы описаны в читаемом справочнике и OpenAPI JSON.

## Бэкапы и смена модели

Производные документы и векторы входят в обычный бекап БД. Полный локальный комплект также включает `.local/embedding-model` и исходники с lock-файлами; окружение Python восстанавливается из lock. Не удаляйте копию закреплённого образа/модели из российского резервного хранилища. Готовый индекс можно пересоздать из исходных задач и модели; потеря индекса не должна означать потерю материалов.

Версия модели включает revision и рецепт обработки. При замене модели нужно изменить идентификатор в сервере и Django и пересчитать векторы; векторы разных моделей не сравниваются. Индексатор постепенно обновляет документы, текстовый поиск продолжает работать. Для переключения без временного неполного семантического индекса потребуется отдельный второй индекс — в этой первой версии его нет.

## Повторяемая проверка

```bash
.venv/bin/python backend/manage.py test core.test_search
.venv/bin/python backend/manage.py benchmark_problem_search --encode-corpus
```

Команда измеряет реальную CPU-векторизацию банка и запросы API, проверяет 20 точных копий и шесть вручную переформулированных условий из `embeddings/evaluation.json`. Результат — `.local/search-benchmark.json`. Это небольшой smoke-набор на локальном CPU, не гарантия полноты поиска по всем математическим формулировкам и не SLA российского VPS. Права дополнительно проверяются изолированными тестами с искусственными данными.

509 задач, 1 018 документов; CPU arm64, модель в два потока, прогретый процесс. 20/20 точных условий найдены первыми; 6/6 переформулировок — в первых двух результатах; 10/10 проверенных решений — в первых 20. Медиана API 78 мс, максимум 92,9 мс на шести переформулировках. Векторизация всего корпуса без записи в БД — 29,22 с. ## Названия и описания

Тот же процесс теперь векторизует названия и описания задач, кружков и каждой версии листка; для тем индексируется полный путь. Решения не примешиваются к метаданным. Индекс `CatalogueSearchDocument` производный: `kind + object_id` однозначно задаёт запись; исходные UUID и права берутся из основных моделей перед ранжированием. В PostgreSQL добавлены HNSW и trigram GIN; локальная SQLite использует ограниченные по памяти CPU-блоки. Новый сервис и GPU не требуются.

`GET /api/v1/catalogue-search?kind=worksheet&q=<текст>&scope=public` возвращает `{kind, results:[{entity,match,excerpt}], semantic,pending,notice}`. `kind=circle/worksheet/topic`, `q` 1–160, `limit` 1–100 (30 по умолчанию), `mode=hybrid/text`. Поля фильтров повторяемые: city для кружков, tag соответствующего справочника, topic для листков, circle для scope=issued. Права и фильтры применяются до ранжирования; число pending тоже ограничено этим срезом. ID обрабатываются без модели. Endpoint разрешён read_only-токену.

Области листков: available/public/mine/all (all только админ), my (назначения школьника), issued (версии, выданные выбранным доступным кружкам). Новая личная версия не скрывает старую опубликованную от остальных пользователей. ФИО и контакты не векторизуются.

Развёртывание прежнее: миграции и `scripts/run_search.sh`; существующий watch-процесс индексирует обе таблицы и не требует ручного старта новой очереди. Новые названия/описания подхватываются сигналами; переименование или перенос темы обновляет пути потомков. После намеренных bulk_update/QuerySet.update, обходящих сигналы, выполните `index_problem_search --rebuild` (либо --rebuild --watch). Обновление fingerprint сбрасывает старый вектор, а запоздалая фоновая работа не перезаписывает новую редакцию.

Добавлено по одному вектору 384 float32 на непустое название/описание задачи, на кружок, версию листка и тему: около 1,5 КиБ сырых векторов на документ плюс строки и индексы БД. Это расчёт формата, не замер полного размера индекса или SLA. При обычном поиске векторизуется только запрос; исходники пересчитываются после изменений. Короткие запросы кэшируются в памяти процесса, число запросов ограничено.

Пользовательская и роботная инструкция: `/#/documentation/catalogue-search`; параметры и форматы — `/#/documentation/api?operation=catalogueSearch`.
