# Пилот: ресурсы, нагрузка и хранение

Замеры от **31.10.2026**: 100 аккаунтов, 6 кружков, 50 листков, 500 задач из сохранённой подборки problems.ru, 300 выдач, 4 800 назначений и 23 750 глобальных результатов. PostgreSQL 17 с pgvector/pg_trgm, Gunicorn, Redis, настоящая CPU-модель E5 INT8, изолированный Tectonic 0.17.0 с TikZ, почтовый воркер, Caddy, локальный архив и S3 по HTTPS. Письма уходили только в тестовый SMTP.

**Минимальный проверенный стенд — Linux ARM64, 2 vCPU и 4 ГиБ RAM** (ядру доступно 3 905 МиБ). Дополнительно проверена общая CFS-квота одного CPU для приложения, БД, модели, TeX, воркеров и Caddy. Это ориентир для 2 vCPU / 50%, а не замер Intel Ice Lake в Yandex Cloud: другая архитектура/частота, диск локальной ВМ вместо сетевых HDD/SSD, ОС и внешние эмуляторы вне общей CPU-квоты. AMD64 через эмуляцию не использовался. **20% CPU и RAM меньше 4 ГиБ не проверены.**

Для первого размещения оставляем **2 vCPU / 4 ГиБ / 50%, HDD 40 ГиБ + SSD 10 ГиБ**. Профиль улучшает использование выделенных ресурсов, не увеличивая размер ВМ. Перед приёмкой в облаке нужен контроль задержек на его оборудовании. Доля vCPU гарантирует время выполнения, а не частоту процессора; реальная производительность может быть выше гарантированной. [Уровни vCPU](https://yandex.cloud/ru/docs/compute/concepts/performance-levels).

## Что проверяли

Каждый сценарий длится 45 секунд: 5 или 10 независимых активных аккаунтов, пауза 0,2 с между запросами. Пять сессий — четыре сотрудника и школьник; десять — четыре сотрудника и шесть школьников. Проверяются HTML, кружки, каталог по 50 задач, личные задачи, листки, журнал всех 50 листков и общая/личная аналитика. Поиск использует разные тексты, чтобы не измерять только кэш query-векторов. Это закрытая модель нагрузки с ограниченной параллельностью, не тест максимального RPS или 100 одновременно работающих пользователей. Вход по паролю, браузерный рендеринг и загрузка всех JS-ресурсов в эти задержки не входят.

Отдельно: три холодных PDF с решениями, старт с пустой БД, первичная индексация, пересоздание служб с предварительным полным бэкапом, 20 писем, а также десять сессий одновременно с повторной индексацией 300 поисковых документов, PDF и полным S3-бэкапом. S3/SMTP — отдельные тестовые службы. Их RAM входит в замер всей ВМ, но не в рабочую память приложения.

Память и cgroup-v2 CPU/OOM считываются каждые 250 мс; CPU-счётчики различают контейнеры до/после пересоздания. Для нагрузочных фаз покрытие телеметрией — 100%. Backend тестового образа побайтово совпал с исходниками: проверены 94 файла. Числа, идентификаторы образов, контрольная сумма кода и раздельные ресурсы служб сохранены в [JSON-отчёте](benchmarks/pilot-linux-arm64-2026-10-31.json).

Финальный повтор всей последовательности одним вызовом CLI использовал пересобранный образ с исправленной отправкой бэкапов: 3 898 нагрузочных запросов, ноль HTTP-ошибок/OOM/swap, покрытие телеметрией 100%, обновление и восстановление завершены. p95 журнала при десяти сессиях составил 7 366 → 566 мс, общей аналитики — 8 023 → 480 мс. Это отдельный повтор на сохранённом тестовом наборе; его тёплый старт не заменяет первичные замеры. Результаты отделены в `one_command_replay` JSON-отчёта.

## Задержки

Десять сессий, **p50 / p95, миллисекунды**; во всех строках HTTP-ошибок нет.

| Семантический поиск | 2522 / 4603 | 300 / 601 | 794 / 1467 | 1489 / 2700 |

При пяти сессиях p95 журнала: 3 197 → 317 мс; общей аналитики: 3 394 → 208 мс. PDF: p50/p95 4,58/4,61 с при прежних лимитах и 1,18/1,19 с в выделенном профиле (по три сборки); одна сборка при одновременном фоне заняла 4,60 с. Малое число PDF не позволяет оценивать устойчивый p95 очереди компилятора.

В обычных сценариях модель участвовала во всех поисках. Во время повторной индексации — в 61 из 63: два запроса штатно перешли на текстовую часть гибридного поиска. Эти ответы HTTP 200 не считаются ошибками, но деградация семантики показана отдельно.

## CPU и память

Старые ограничения использовали в стресс-сценарии лишь около 0,47 CPU при двух доступных: web тормозился своей квотой 0,30. Выделенный профиль использовал 1,54 CPU. При общей квоте 1 CPU обычная нагрузка занимала 0,98 CPU: **под такой непрерывной нагрузкой запаса CPU почти нет**, хотя запросы завершались. Поэтому снижать долю до 20% по этим результатам нельзя.

| Служба | CPU: общий → выделенный | Приоритет CPU в выделенном профиле | Предел RAM |
| --- | ---: | ---: | ---: |
| web | 0,30 → 1,25 | 1024 | 512 МиБ |
| PostgreSQL | 0,30 → 1,00 | 768 | 512 МиБ |
| Redis | 0,05 → 0,10 | 512 | 128 МиБ |
| Модель | 0,75 → 0,75 | 384 | 1024 МиБ |
| TeX | 0,30 → 0,75 | 256 | 512 МиБ |
| indexer | 0,15 → 0,25 | 128 | 256 МиБ |
| mail | 0,05 → 0,10 | 128 | 192 МиБ |
| backup | 0,10 → 0,15 | 64 | 256 МиБ |

Это верхние границы, не резервирование 4,35 ядер. При конкуренции службы делят имеющиеся CPU по весам. `initialize` отдельно ограничен 1 CPU / 384 МиБ. Прежний профиль общего хоста остаётся по умолчанию; выделенный включается только через `resource_profile: dedicated-pilot`.

Рабочая память постоянного стека достигала примерно **1,53 ГиБ** при фоне, первичная индексация — 1,36 ГиБ. Минимум доступной памяти всей ВМ в нагрузочных фазах — **1,42 ГиБ**, включая ОС, Docker, Caddy, монитор и S3/SMTP-эмуляторы. Swap не использовался, OOM в принятом прогоне не было. Это измеренные пики, не сумма memory limits (3 392 МиБ). Меньшую RAM по этому тесту не рекомендуем.

Первый старт с пустой БД занял 91 с, индексация нового набора — ещё 112 с. Проверенное пересоздание служб — 72 с плюс предварительный бэкап. Миграций новой схемы при этом не было: будущую тяжёлую миграцию эти числа не оценивают. После обновления и восстановления совпали пользователи, задачи, листки, результаты и назначения.

| Содержимое | Измерено |
| --- | ---: |
| Рабочая БД, включая индексы и служебные данные | 41,6 МиБ |
| Индексы пользовательских таблиц | 20,5 МиБ |
| WAL после нагрузки/обновления | 80 МиБ |
| Весь каталог PostgreSQL | 144,3 МиБ |
| Один полный зашифрованный архив | около 118 МиБ |
| Две локальные копии | около 236 МиБ |
| 14 удалённых копий | около 1,61 ГиБ |
| Два подготовленных набора образов: сжатые уникальные blobs | около 0,62 ГиБ |
| Те же наборы: распакованные уникальные слои | около 1,74 ГиБ |

Архив создавался за 47–53 с, S3-отправка заняла ещё 7–9 с при лимите backup 0,15 CPU. Пик Python RSS — 54 МиБ; пик памяти cgroup с дочерними процессами и заряженным файловым кэшем — 176 МиБ, ниже лимита 256 МиБ. Это отдельный замер; полный бэкап на фоне запросов занял 54 с. Размеры и время могут немного различаться между сборками.

В финальном повторе переиспользованный воркер достиг примерно 256 МиБ по lifetime-счётчику cgroup, включая файловый кэш; его рабочий набор при фоне достиг 97 МиБ, Python RSS — 54 МиБ. OOM не было. Пик отдельного запуска 176 МиБ не является верхней границей всей жизни воркера. Полный бэкап занял 53 с, обновление — ещё 61 с после предварительного архива; минимум доступной памяти ВМ при фоне составил 1 383 МиБ.

Из 118 МиБ около 86 МиБ приходится на модель, 23 МиБ на TeX, 2,6 МиБ на исходники/настройки и 6,5 МиБ на БД (компоненты отдельно упакованы tar+gzip level 1). Вынос неизменяемых артефактов из ежедневных архивов на пилоте сэкономит менее 3 ₽/месяц, поэтому **формат оставлен полным и самодостаточным**. Не добавляем зависимость восстановления от цепочки манифестов и отдельно доступного артефактного бакета.

HDD 40 ГиБ оставляем: ориентир для планирования — до 10 ГиБ на ОС, Docker, журналы и конфиги; 6 ГиБ на два набора образов с распаковкой/скачиванием; 3 ГиБ на локальные архивы и рабочий dump; 4 ГиБ на временные файлы проверки/восстановления. Это запас для планирования, не измеренная занятость чистой Ubuntu. Остаток держим свободным. Сборки и BuildKit-кэш на рабочей ВМ не размещаем. На SSD 10 ГиБ фактический кластер занял около 0,15 ГиБ; место для WAL, индексов и будущих миграций сохраняем. Скорость сетевых HDD/SSD этим стендом не измерена.

S3-ошибка теперь не вызывает новый полный архив каждую минуту: воркер повторяет upload готового файла. Если прошёл интервал снимка, создаёт свежую локальную копию, даже при продолжающемся сбое. Локальная ротация выполняется независимо от S3 и сохраняет минимум две полные копии. Успех/здоровье отмечаются только после успешной удалённой проверки, временем самого снимка. Перед обновлением всегда создаётся свежий архив. Повтор уже завершённого PUT с теми же размером и SHA не создаёт новую S3-версию. Эти случаи проверены и тестами, и реальным отказом соединения с эмулятором.

## S3 versioning и реестр

В Terraform текущий объект становится удалённым через 14 дней; его нетекущая версия очищается через 1 день, отдельно удаляются оставшиеся маркеры и незавершённые multipart-загрузки. Прежние 14 дней для нетекущих версий фактически удваивали срок хранения тела. Приложению право удаления не выдаётся. Из-за ежедневной обработки lifecycle для бюджета стоит учитывать до 17 размеров архива, не ровно 14. [Правила S3 lifecycle](https://yandex.cloud/ru/docs/storage/operations/buckets/lifecycles).

На HTTPS-эмуляторе проверены конфигурация правил, чтение версии после создания delete marker, фактическое удаление версии по VersionId и исчезновение маркера. **Автоматический планировщик Yandex Cloud не проверялся**: облачные ресурсы не создавались. После размещения следует проверить `list-object-versions` владельцем бакета после первого срока ротации.

Полный `mode=max` кэш опубликован в локальный OCI-реестр и использован повторной сборкой. Измерено: текущие образы 313 МиБ, предыдущие 323 МиБ, граф кэша 404 МиБ. За счёт общих слоёв суммарно занято **около 729 МиБ**, из них добавка кэша — 91 МиБ; неиспользуемые blobs двух сборок добавили около 2 МиБ. Локальный том сборщика — 1,88 ГиБ. GC с `maxUsedSpace=2GB` — целевой объём локального кэша, не жёсткая квота активной сборки и не лимит registry.

Правила хранения:

1. Рабочие образы и кэш имеют разные префиксы (`/plusfolio` и `/build-cache`), при необходимости — разные реестры.
2. На релизный префикс не ставим автоматическое удаление. Сохраняем текущий, резервный проверенный набор и версии, на которые ссылаются ещё хранимые бэкапы. Один лишь принцип «две последние версии» не защищает старый работающий релиз.
3. Для кэша есть [пример политики](../deploy/yandex/registry-cache-policy.example.json): сохранить последнюю версию каждого пакета, удалять нетегированные старше 7 дней с дополнительным днём мягкого удаления. При другом префиксе его нужно изменить в примере.
4. Политику сначала создать в состоянии `DISABLED`, проверить dry-run: удаление не должно затрагивать `/plusfolio`. В облаке эта политика нами не применялась. [Семантика KEEP/SOFT_DELETE](https://yandex.cloud/ru/docs/cloud-registry/concepts/lifecycle-policy).
5. На сервере удалять только конкретные старые ссылки после сверки с текущим/резервным `images.json`. Общие `docker system prune`, `image prune -a` и очистка чужих томов в установщик не входят. Экспорт образов для автономного восстановления хранить вне системного диска в паре с JSON; `backup.key` — отдельной защищённой копией.

Для условных 720 часов: COLD — 1,2672 ₽/ГиБ·месяц, запись — 1,39 ₽/1000 операций, чтение/HEAD — 1,15 ₽/10 000. Архивы с запасом lifecycle и ежедневными multipart-загрузками дают примерно **3–4 ₽/месяц**. COLD не имеет годового минимума ICE. [Тариф Object Storage](https://yandex.cloud/ru/docs/storage/pricing).

Реестр с измеренными образами и кэшем помещается в свободные 720 ГиБ·ч за месяц, если этот общий лимит ещё не занят другими проектами. Без свободного лимита — около **4 ₽/месяц** по показанному тарифу примерно 0,007 ₽/ГиБ·ч. При частых сборках и большем банке нужно учитывать новые слои и окно очистки. [Тариф Cloud Registry](https://yandex.cloud/ru/docs/cloud-registry/pricing). Это расходы хранения пилота; ВМ, диски, IPv4, домен и Postbox считаются отдельно.

## Повторение

Нужен **отдельный тестовый Linux Docker с cgroup v2/cgroupfs**, примерно 2 CPU / 4 ГиБ и готовыми образами той же архитектуры. На Mac использовалась отдельная Colima ВМ; начальная сборка/скачивание образов выполняются до нагрузки. Драйвер Docker на общем/рабочем сервере менять ради теста нельзя. Системный systemd-driver и CPU-ограничения Yandex Cloud этим стендом не воспроизведены.

В свежем отдельном checkout без `.deploy/env`:

```bash
python3 deploy/check_capacity.py \
  --app-image APP_IMAGE --tex-image TEX_IMAGE --embedding-image EMBEDDING_IMAGE \
  --seconds 45 --output /private/path/capacity.json
```

Генератор создаёт только зарезервированные `@capacity.example.test` аккаунты, собственный Compose project, родительский cgroup, тестовые SMTP/S3 и volumes. Письма реальным пользователям не отправляются. В конце тестовые volumes удаляются; `--keep` оставляет только этот стенд для диагностики, `--reuse` повторяет его нагрузку без нового импорта. Существующее обычное развёртывание он не принимает. Для сравнения места двух сборок добавьте `--previous-release /private/path/images-previous.json`; соответствующие образы должны быть заранее загружены. При неполной телеметрии отчёт не помечается завершённым.

Тест не создаёт облачных ресурсов и не запускает Terraform apply. Чистая сборка требует интернета для зависимостей и первого прогрева TeX; сервер из готового релиза их не скачивает. GitHub CI проверяет защиту хоста, backup/retry, вычисление метрик и регрессии; нагрузочный отчёт — отдельный измерительный прогон, его не подменяет macOS/SQLite-тест.
