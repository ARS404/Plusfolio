# Обязательный контракт для роботов

Версия: 1.1.0. После авторизации агент обязан получить `GET /api/v1/documentation?audience=robot` и до выполнения сценария прочитать применимые `mandatory_instructions`. Эти поля находятся в начале JSON; в Markdown и интерфейсе правила также стоят перед остальными разделами. OpenAPI содержит тот же реестр в `x-plusfolio-mandatory-instructions`.

- `robot-required-rules` — обязательные правила диалога, прав, ID, остановки и продолжения для всех агентов.
- `robot-worksheet-upload` — обязательный сценарий загрузки листка для преподавателя и администратора. С токеном только для чтения инструкция доступна, но `can_execute=false`: создавать объекты нельзя.

Полный протокол отдаёт API, чтобы роли и разрешённые операции не расходились с фактическим аккаунтом:

```text
GET /api/v1/documentation/robot-required-rules?audience=robot
GET /api/v1/documentation/robot-worksheet-upload?audience=robot
GET /api/v1/documentation?audience=robot&download=markdown
```

В интерфейсе: `/#/documentation?audience=robot` и `/#/documentation/robot-worksheet-upload?audience=robot`.

При загрузке листка агент для каждой задачи сначала ищет аналоги и задаёт дополнительные вопросы о выборе существующей или создании новой задачи, темах и тегах. Новые темы и теги создаются только по явному запросу и только администратором. Для выбранной существующей задачи нельзя молча менять неизменяемые метаданные или создавать копию. После всех задач агент отдельно согласовывает название, описание, темы, теги и порядок задач листка, получает подтверждение и создаёт личный листок.

Ответы `POST /api/v1/materials/problem` с HTTP 201 уже содержат `id` (UUID), `public_id` (P-ID), `number`. Ответ создания листка содержит `public_id` (W-ID), `document_id`, `id` версии и `revision`. Агент обязан сохранить и вывести эти значения. Внутренние связи строятся по UUID, а не по названиям или публичным номерам.

Реальные ответы пользователя обязательны: выбранная по умолчанию опция, молчание или тайм-аут не считаются подтверждением. При наличии инструмента дополнительных вопросов агент использует его; иначе задаёт отдельный явный вопрос и ждёт ответа. При неизвестном результате POST агент сначала восстанавливает состояние, не повторяя создание вслепую.

Это нормативный контракт агента. Сервер проверяет доступ и корректность данных, но не подтверждает факт человеческого диалога; флаги согласований не являются параметрами API. Изменения самого протокола должны сопровождаться обновлением версии, проверками манифеста, ролевой видимости и экспортируемой документации.

Версия 1.1.0 требует обсуждать задачи по одной в порядке листка, при отсутствии решения предложить и согласовать собственное либо запросить решение у пользователя. Согласование решения может занимать несколько вопросов. До публикации каждой задачи обязательна точная сборка и проверка обоих PDF; перед созданием листка также проверяется весь листок. Инструкция robot-tex-build и GET /api/v1/tex/toolchain предоставляют закреплённый пакет локального предпросмотра. [Процесс и команды](tex-preflight.md).
